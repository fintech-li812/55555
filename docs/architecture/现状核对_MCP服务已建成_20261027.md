# 现状核对：我们的计算引擎已经是一个可用的 MCP 服务

日期：2026-10-27 傍晚。
性质：**实测核对**，不是设想。以下每条都有当场跑出来的输出为证。

---

## 0. 一句话结论

**你想让"后端和千问办公交互"——这条路已经铺好了，只是方向跟你说的是反的：**
不是我们的后端去调千问的 MCP，而是**千问办公接入我们的 MCP 服务**。
后者是 MCP 的标准形态（Agent 是客户端，工具是服务端），而且我们的服务已经能跑。

## 4. 这对架构意味着什么

**好的方面（全是实测得来的，不是愿望）：**

1. **金额确定性保住了。** 算钱的是我们自己的 Decimal 代码（工具 6），千问只是调用方。AI 可以参与调度，但金额由死代码产出——**红线不破**。
2. **不用移植 Node 了。** Python MCP 服务直接被千问调用，整个 S2 阶段可以取消（那 1644 行不用搬）。
3. **"以千问办公为核心"这次真的很实。** 不是"住在它家"（托管），而是"给它当手艺"（千问的 Agent 在调度我们的工具）。后者是深耦合，前者只是租赁。
4. **AI 可以做。** 千问的 Agent 负责理解意图、挑选工具；金额由工具算出。分工干净。

**代价与缺口（必须知道）：**

1. **stdio 只能本机。** 进程由千问桌面端在本机拉起，所以千问桌面端和我们的服务必须在同一台机器。
   → 推论：**你关机，它就没了**。这与最初"我关机它还在"的目标冲突，需要靠"迁到服务器 + 换 HTTP 传输"解决。
2. **存储是唯一的功能缺口。** `database: unavailable`，所以工具 8（保存）和 9（回查）目前跑不了。
   这正好对应 D4 的答案——要么上千问内置库（标准版 98 元/月），要么自己接一个库。
3. **"我们调千问的 Skill"这条路仍未证实。** Skill 通常是给千问内部 Agent 用的，没有对外接口。
   在拿到证据前，不应对外声称"在调用千问 Skill"。

## 5. 下一步（按性价比排序）

1. **给 MCP 服务加 HTTP 传输模式**（`streamable-http` 或 `sse`），不改现有 stdio 逻辑，只是多一种接法。
   好处：本机千问仍走 stdio；服务器部署走 HTTP，前端与远程后端都能调——**一颗心脏，多种接法**，顺带解决"关机还在"的问题。
2. **把存储补上**，让工具 8/9 真正可用。
3. 前端按你的效果图做，只消费后端结果，一个数都不自己算。

第 1 步是纯增量、不动现有代码，风险最低，收益最大。
