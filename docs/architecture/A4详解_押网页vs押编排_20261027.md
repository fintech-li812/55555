# A4 详解：押网页 还是 押编排

> 写于 2026-10-27，供讲座现场提问与回来审批。
> 所有金额举例仍为合成演示值（SYNTHETIC），不涉及真实企业数据。

---

## 0. 三十秒人话版

- **押网页** = 我在千问的商场里**租了间铺面，自己当老板**。
  铺子里的机器是我造的，账是这台机器算的。客人推开 `.qwenwork.host` 那扇门就进来了，他甚至不需要知道千问是什么。**千问是房东兼物业。**

- **押编排** = 我不开店了，改行**当千问手底下的手艺人**。
  用户不来我的门面，他直接跟千问说："帮我把这个月的现金流跑一遍。" 是千问在听、在想、在安排先做哪一步，最后喊我们的手艺去干活。**用户记住的是"我能让千问帮我做事"，不是"我有个网址"。**

一句话区别：**一个是"我的东西放在千问那儿"，另一个是"我长在千问身上"。**

## 1. 九个维度的逐条对比

| # | 维度 | 押网页（我们现在的方案） | 押编排 |
|---|---|---|---|
| 1 | 用户怎么接触 | 打开一个网址 | 跟千问说一句话 |
| 2 | 谁能用 | **任何人**，不需要千问账号 | 只有千问用户，且要会描述需求 |
| 3 | 对外名片 | 一个 `.qwenwork.host` 链接，可直接发给客户 | 说不清，只能说"在千问里找我" |
| 4 | 谁在算钱 | 我们移植的 Node 代码，**确定性** | 取决于编排实现（见第 2 节，这是生死线） |
| 5 | 数据存在哪 | 千问内置 Supabase 库，结构化 | 未知：可能是文档/表格/网盘/技能状态 |
| 6 | 搬得走吗 | **搬得走**，Node 代码换个机房照样跑 | **搬不走**，手艺长在千问身上 |
| 7 | 速度 | 秒级，实测网关 30 秒上限绰绰有余 | 多一步 LLM 调度，慢，且消耗 token |
| 8 | 成本 | 只有可能的套餐费（标准版 98 元/月） | 每次运行都要烧 token，用得多就贵 |
| 9 | **"以千问为核心"的成色** | **弱**：千问只是托管商（答辩 Q1 我方认输过） | **强**：千问是干活的那一方，删账号即全灭 |

**第 9 行是这份文档的核心。**
"以千问办公为核心" 这句话最怕的质疑是：*"搬去别家也能跑，凭什么叫以千问为核心？"*
——押网页对这一问**只能认输**（事实如此）。而**押编排是唯一能把这一问翻案的路**，因为搬不走的才配叫核心。

---

## 2. 生死线：A4 必须问清"算钱的到底是谁"

押编排这条路有个能让我们当场暴死的分岔：

- **情形甲（工头派活）**：编排只负责排顺序、传文件、调工具，**真正算钱还是我们那套死代码**。
  → 这条路成立，而且很漂亮。
- **情形乙（AI 自己算）**：由大模型现场读表、现场加总。
  → **对我们的项目直接出局。**
  理由：我们做的是对账，差一分钱整份报告作废，而 LLM 天生是"大概率对"。金额绝不能交给概率。

**所以 A4 不是一道题，是四道，必须一起问：**

| 编号 | 要问的事 | 为什么致命 |
|---|---|---|
| **A4a** | 编排里"算"这一步，是 AI 自己在算，还是它去调一个外部工具来算？ | 决定情形甲/乙，直接决定这条路是生是死 |
| **A4b** | 编排能不能调用**我们自己写的确定性代码**？如果能，是以什么形态接进来——技能、MCP、还是 HTTP 接口？ | 决定我们那 1644 行移植成果能不能复用，还是要另做一份 |
| **A4c** | 编排跑完的结果存到哪？能进结构化数据库吗，还是只能落到文档/表格/网盘？ | 决定"留痕 + 可回查 + 可导出"这三条还能不能成立 |
| **A4d** | 编排做出来的东西，有没有一个可以发给别人访问的公开 URL？ | 决定我们还有没有对外交付物 |

## 3. 现场可以直接照着念的问法

> "我们在做一个制造业现金流工作台，核心是一套已经验证过、能用 100 项回归测试的精密计算逻辑。
> 我们现在有两种做法，想请你们判断哪一种才算'以千问办公为核心'：
> **第一种**是做一个动态网页，把计算逻辑整个搬进网页的 Node 后端，对外一个网址；
> **第二种**是不做网页，改成让用户在对话里说一句话，由千问的任务编排去调度我们的计算。
> 我想问的是——
> **（1）** 你说的编排，是让模型自己算数，还是它去调一个确定性的工具？我们的金额差一分钱就算废，不能交给概率。
> **（2）** 编排能调用我们自己写的代码吗？以什么形态接进来？
> **（3）** 编排跑完的结果能进数据库吗？还是只能落到文档里？
> **（4）** 哪种才算你们认可的'以千问办公为核心'？"

**第（1）问最重要，也最容易得到含糊答案。** 如果对方说"模型会调用工具"，要追一句：**"那工具是我们的代码，还是你们平台的通用能力？"** 通用能力 = 情形乙 = 我们出局。

## 4. 我的推荐：一颗心脏，两个入口

**不要二选一。** 建议形态：

```
                 千问账号
    ┌──────────────────────────────┐
    │  对外：网页网址   对内：对话编排  │
    │   （任何访客）    （千问用户）   │
    │            ↓ 共用 ↓           │
    │       Node 计算内核（确定性）    │
    │            ↓                 │
    │          同一个存储            │
    └──────────────────────────────┘
```

三条不可让步：
1. **心脏必须是确定性代码**——不管从哪扇门进来，算钱的都是同一份移植好的 Node 内核，整数分运算，绝不让 AI 做加法。
2. **对外那扇门要保住**——发给客户一个链接就能看，这是唯一拿得出手的交付形态。
3. **对内那扇门是加分项，不是救命稻草**——它决定的是"以千问为核心"这句话的成色，不影响系统能不能用。

## 5. 回来怎么拍板（If → Then）

| 下午问到的答案 | 我们接下来怎么做 | 已投入的资产会不会作废 |
|---|---|---|
| **"押网页"** | 右门暂时封着，主线不变，继续 Stage 2 | 不作废，全部有效 |
| **"押编排，且是工头派活（情形甲）"** | 心脏不动，**右门从"以后再说"提到"先做"**，对外网页仍保留 | 不作废，加一条入口 |
| **"押编排，但是 AI 自己算（情形乙）"** | **拒绝这条建议**，并向对方说明我们为什么不能用概率算账；对外沟通口径改为"页面型应用" | 不作废，我方主张成立 |
| **"编排调不了你们自己的代码"** | 右门降级为"只做展示，不负责算"，心脏仍留在网页里 | 不作废 |
| **对方也说不清** | 按"押网页 + 右门暂缓"推进，把 A4 标记为**未决**，对外不说满话 | 不作废 |

**结论：A4 的任何答案都不会让我们推翻这半天的工作。** 唯一会让架构重画的情况不是 A4 本身，而是"编排能调度、且必须用平台通用能力替代我们的计算逻辑"——那等于产品性质变了，不是我们选不选的问题。

---

## 6. 这条文档的真话部分

- **押网页在"以千问办公为核心"这个命题上，成色确实是弱的。** 这一点我在答辩记录 Q1 已经认输过，不因为换了个场合就改口。
- **押编排成色强，但带着三个真代价**：慢、烧 token、以及最关键的——算钱的确定性可能被稀释。
- 所以推荐形态本质是：**用押网页保住正确性和对外交付，用押编排去争取那句"以千问为核心"的成色。**
