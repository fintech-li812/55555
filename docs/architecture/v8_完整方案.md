## 一、方案定位

> **本节已按 v8.2 路线修订重写。**

本方案以**千问办公 AI 平台为后端 / 中枢**：千问负责意图理解与流程编排，**通过 Skill 承载 workflow、通过 MCP 调用各类算法与数据能力**；数值计算全部在自有后端完成，不由千问表格公式承担。

**三层分工（v8.2 定稿）**：

```
用户 / 前端页面
      │  自然语言 或 HTTP 请求
      ▼
┌──────────────────────────────────────┐
│  千问办公（后端 / 中枢）               │
│   · Skill  → workflow 编排             │
│   · 对话智能体 → 意图识别与结果解释     │
│   · 通过 MCP 调用下方全部能力          │
└──────────────┬───────────────────────┘
               │  MCP（stdio / streamable-http）
               ▼
┌──────────────────────────────────────┐
│  自有后端（Python + MySQL）            │
│   · 算法引擎：现金流 / 三层风控 / 压测  │
│   · 数据表格读取与清洗                 │
│   · MySQL 落库与回查                   │
│   · Agent 动作：钉钉 / 企业微信推送     │
└──────────────────────────────────────┘
```

**本版本核心定位**：不预设平台能力的上限；**但也不把方案成立与否押注在平台能力上**。凡是能在后端用代码确定性实现的（计算、阈值、判定、落库），一律在后端实现，千问只负责调度与解释。所有阈值、规则、参数都标明来源与适用边界，避免把"设计意图"写成"已验证事实"。

### 1.4 合规依据（v8.2 重写 —— 本条存在真实风险，必须正面处理）

**v8.2 路线变更后，合规论证口径必须改**，不能再用 v7 那句"核心逻辑由千问办公原生能力完成"。

**新的论证口径**：本方案的**业务编排层在千问办公内**——workflow 以 Skill 形式注册在千问中，全部能力以 MCP 工具形式由千问调用与调度；千问是系统的入口、大脑与调度中枢。后端承担的是**确定性数值计算**，属于工程实现分层，不是脱离平台自建一套独立系统：没有千问的调度，后端不会自行产生任何业务动作。

> **依据**：《[比赛全称]》参赛规则第 [X] 条："核心业务逻辑须以平台原生能力实现，外部工具仅可作为辅助接口使用。"（规则编号与原文待填入，**必须由参赛队员向主办方确认后补全**。）

**⚠️ 风险提示（必须让队员知道）**：若主办方对"平台原生能力"的解释是"计算也要在平台内跑"，本方案的后端计算部分会被质疑。**这一条不是靠话术能糊弄过去的**，答辩前必须二选一做完：

1. **向主办方书面确认**"外部 MCP 工具 / 自定义 Skill 是否算平台原生能力"，拿到明确答复；
2. **准备第二套演示**：千问侧完整走一遍 Skill workflow（对话驱动、工具调用记录可见），证明流程确实跑在千问里，后端只是被调用的工具库。

**核验点**：主办方评审表通常关注"是否脱离平台自建系统"。建议答辩话术——"系统的每一次业务动作都由千问发起、由千问编排、结果回到千问解释；后端工具不会自行动作，等价于平台的一个外挂函数库。"

### 1.6 方案核心亮点

1. **深入**：现金流按经营/筹资/投资三类建模 + 管理会计内部信息 + 四层因果穿透（预警→归因→推演→根因）
2. **动态**：预警阈值基于历史同期滚动分位数动态调整，旺季不误报、淡季不漏报（数据满 12 个月启用）
3. **相对化（v8 核心升级）**：**所有预警线不再使用绝对金额，统一改为"相对指标 + 行业分位数"**。现金缓冲预警线 = 月均经营性流出M × 系数K黄/K红；审批分界线 = 月均业务规模 × 比例区间。**企业规模不同不再影响判定结果**，小微企业与大集团共用同一套逻辑，只需更换"月均流出"这个规模锚点
4. **三层风控模型（v8 核心升级）**：融合三篇核心文献方法论——第一层「数据质量门禁」基于 Benford 律 + Myer 指数构造双质量因子，在数据进入计算前先识别粉饰与舞弊（杨贵军等，2022）；第二层「财务健康判别核心」采用改进 DEA-DA 判别分析，兼顾规模收益、指标性质（正/逆指标）、投入产出比与指标交互，输出可解释的判别得分（马秀颖等，2026）；第三层「异常样本复核」用 Benford-随机森林识别具体舞弊样本点，提供"哪个指标、哪条记录"的可追溯证据（孙玲莉等，2021）
5. **闭环**：Agent 有明确动作权限与验证机制，确保每个"推动"动作都有"验证"，不止于"建议"
6. **可验证**：到账状态通过银行流水自动对账或凭证上传+抽检验证，杜绝虚报
7. **常态化**：压力测试每月自动跑，生成偿债安全健康度报告，管理层定期看到最坏情况
8. **可追溯**：例外审批每季度回溯，异常部门触发审计检查
9. **普适**：不问行业，只问事实。5 个引导式问题自动生成初始参数，覆盖多行业×多场景的组合空间
10. **自适应**：参数能根据实际使用情况递推修正，向"企业专属"方向演进

### 1.7 前端与 MCP 的链路现状（v8.2 新增 · 现状核查结论）

**结论：目前「用 MCP 接收前端请求」这条链路不存在。** 前端与千问各走各的路，两条链路不交汇。

**实际现状（2026-10-28 服务器实测）**：

```
前端页面(浏览器)
   │  fetch('/api/calculate','/api/save','/api/query', ...)
   ▼
public_server.py :8000  ──直接 import service.py──▶ 算法引擎 + MySQL
   （cf-workbench 服务）

千问办公
   │  MCP / JSON-RPC
   ▼
entry.py http :8123  ──▶ 9 个 MCP 工具 ──▶ 同一套 service.py + MySQL
   （cf-mcp-http 服务，nginx 反代 https://<域名>/mcp）
```

**三条实测事实**：

1. **前端零处调用 MCP**。整个 `web/` 目录（工作台页、v8 页、v10 页、后端控制台页）中检索 `/mcp` 无任何命中；页面只调 `/api/*` 共 7 个接口（`status / sources / calculate / save / query / audit / readiness`），全部走 8000 端口。
2. **MCP 端点活着且可用**，但只有千问侧会用：经 HTTPS 完整握手后可 `tools/list`，返回 9 个工具——`get_workbench_status`、`list_manufacturing_sources`、`inspect_manufacturing_source`、`get_manufacturing_readiness`、`get_manufacturing_data_audit`、`calculate_manufacturing_cashflow`、`read_cashflow_result`、`save_cashflow_result`、`query_cashflow_result`。
3. **两条链路共用同一套业务代码**（`service.py`），所以结果恒等，但**调用路径完全独立**——前端的请求一次都没有经过 MCP。

**这与 v8.2 定稿架构不符**。定稿要求"千问办公作为后端/中枢，前端请求也应经由千问编排后落到 MCP 工具"，现在前端是绕过千问直连后端的。

**整改方向（三选一，建议第 2 种）**：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| ① 前端直连 MCP | 页面直接 POST `/mcp`，自己组 JSON-RPC | 小 | **不推荐**：绕过千问，等于千问在架构里没有位置，与"千问为中枢"自相矛盾，答辩致命 |
| ② **后端做 MCP 客户端**（推荐） | 前端仍调 `/api/*`，但 `public_server.py` 内部不再直接 import 引擎，改为以 MCP 客户端身份调 8123 的工具 | 中 | 链路变成"前端→后端→MCP→引擎"，MCP 成为唯一能力入口，架构自洽；多一跳，需处理 session 与超时 |

## 二-A、方法论升级：融合三篇核心文献的三层风控模型（v8 新增）

> 本章是 v8 相对于 v7 最本质的升级。v7 的预警逻辑是"现金流缓冲 + 规则阈值"的工程化实现，缺乏学术方法论支撑。v8 在保留全部工程实现的基础上，引入三篇财务风险预警领域的最新研究成果，将方案从"设计文档"升级为"有理论支撑的可落地系统"。

### 2-A.1 为什么需要方法论升级

**评委必问**："你的预警逻辑凭什么有效？阈值怎么定的？判定模型有没有实证依据？"

v7 的回答是"基于行业财报统计 + 人工经验"。这个回答在演示环节够用，但在答辩环节会被追问方法论缺陷。v8 的回答是：**我们的判定模型融合了三篇已发表研究的实证结论，每一层都有学术依据**。

### 2-A.2 三篇核心文献的方法论摘要

| 文献 | 核心方法 | 解决了什么问题 | 本方案中的定位 |
|---|---|---|---|
| 杨贵军等（2022）《统计与决策》 | Benford 律 + Myer 指数构造**首末位质量因子**，引入 BP 神经网络，形成 BM-BP 模型 | 上市公司粉饰财务数据会降低预警准确率；双质量因子（首位+末位）比单一 Benford 因子更有效 | **第一层：数据质量门禁** |
| 马秀颖等（2026）《数理统计与管理》 | **改进 DEA-DA 判别分析**，考虑规模收益、指标性质（正/逆指标）、投入产出比、指标交互 | 传统判别分析对规模收益、指标性质、投入产出考虑不足；SVM 非线性目标函数不可解释 | **第二层：财务健康判别核心** |
| 孙玲莉等（2021）《数量经济技术经济研究》 | **Benford-随机森林**，用 Benford 因子标记舞弊样本点，随机森林集成提升精度 | 单一模型预警效果有限；随机森林避免过拟合且稳健 | **第三层：异常样本复核** |

### 2-A.3 三层模型融合逻辑

```
原始财务数据
    ↓
═══ 第一层：数据质量门禁（Benford + Myer）═══
    对15个财务比率指标的首位数字做 Benford 律 χ² 拟合优度检验
    对末位数字做 Myer 指数检验（M>20 判定为质量风险）
    构造 Benford 因子 Bₖ 与 Myer 因子 Mₖ（首位/末位观测频率偏离最大的数字标记）
    输出：数据质量得分 Q ∈ [0, 1]
    ↓
    若 Q < 阈值 → 标记"数据质量风险"，进入第三层复核
        （此处描述的是**流程**：低质量数据必做复核；
          对应的**定级**结论见 2-A.7，二者是流程与结论两个层面）
    ↓
═══ 第二层：财务健康判别核心（改进 DEA-DA）═══
    7 个核心财务比率（经决策树筛选）作为输入
    指标按经济含义标注为"正指标/逆指标"
    投入产出指标按 DEA 逻辑配对（如：利息保障倍数→投入，EBITDA/利息支出→产出）
    考虑规模收益可变（BCC 模型），避免大企业天然得分高
    输出：财务健康判别得分 D ∈ [-1, 1]
    ↓
    若 D < 0 → 标记为"财务风险"
    ↓
═══ 第三层：异常样本复核（Benford-随机森林）═══
    对第二层判定为"风险"的样本，用 Benford-随机森林 二次复核
    Benford 因子作为额外特征输入随机森林
    输出：舞弊概率 P ∈ [0, 1]
    ↓
    若 P ≥ 0.7 → 标记"高风险+疑似粉饰"（阈值符号统一为 ≥，与 2-A.7 一致）
    若 P < 0.3 → 降级为"黄灯"，仅为经营性问题
    ↓
最终预警等级 = FUSE(Q, D, P)，判定表见 2-A.7
```

### 2-A.4 第一层详解：数据质量门禁（基于杨贵军等，2022）

**核心思想**：上市公司存在粉饰财务数据美化经营状况的动机。如果输入数据本身不可信，再精妙的计算模型也会得出错误结论。因此**在数据进入计算前，先做质量检验**。

**具体实现**：

**Step 1：Benford 律首位数字检验**

对每个财务比率指标 Xₖ，统计其首位数字 d（1~9）的观测频率 e_{k,d}，与 Benford 理论频率对比：

```
Benford 理论频率：f_B(d) = log₁₀(1 + 1/d)，d = 1,2,...,9
χ² 统计量：χ² = N × Σ[(e_d - f_B(d))² / f_B(d)]，d = 1..9
```

若 χ² > 20.09（10% 显著性水平临界值），判定该指标**首位数字分布偏离 Benford 律**，存在数据质量风险。

**Step 2：Myer 指数末位数字检验**

将数据按数值大小分为区间1（较小值）和区间2（较大值），分别统计末位数字 0~9 的分布频率，计算 Myer 指数：

```
Myer 指数 M = [Σ(f₁,ⱼ × b₁,ⱼ + f₂,ⱼ × b₂,ⱼ) / Σ(f₁,ⱼ × b₁,ⱼ + f₂,ⱼ × b₂,ⱼ)] × 100 - 10
```

其中 b₁ = 1,2,...,10，b₂ = 9,8,...,0 为权重系数。

若 M > 20，判定该指标**末位数字存在偏好性堆积**，数据质量存疑。

**Step 3：构造质量因子**

对每个指标 Xₖ，找出首位/末位数字中观测频率与理论频率偏差最大的数字，作为"风险数字"：

```
h_B(k) = argmax_d |e_{k,d} - f_B(d)|    # Benford 风险数字
h_M(k) = argmax_j |n_{k,j} - m_j|       # Myer 风险数字
```

构造 0/1 因子：

```
B_ks = 1，若 Xₖ 的首位数字 = h_B(k)；否则 0
M_ks = 1，若 Xₖ 的末位数字 = h_M(k)；否则 0
```

**Step 4：综合数据质量得分**

```
Q = 1 - (Σ Bₖ + Σ Mₖ) / (2 × 指标数)
```

Q 越接近 1，数据质量越高；Q 越接近 0，数据质量越差。

**算法等价表达（v8.2：以下公式仅用于说明规则，实际由后端代码实现）**：

```excel
# 首位数字提取
首位数字 = VALUE(LEFT(SUBSTITUTE(TEXT(A2,"0.000000"),"0.",""),1))

# Benford 理论频率
Benford理论频率 = LOG10(1+1/首位数字)

# χ² 贡献值
χ²贡献 = 样本量 × (观测频率 - Benford理论频率)² / Benford理论频率

# Myer 指数（末位数字检验）
末位数字 = VALUE(RIGHT(TEXT(A2,"0.000000"),1))
Myer指数 = 末位分布偏离度 × 权重系数

# 数据质量得分
数据质量得分 = 1 - (Benford因子之和 + Myer因子之和) / (2 × 15)
```

**实证依据**（杨贵军等，2022）：

| 指标 | χ² 值 | 是否偏离 Benford 律 | 对应质量因子 |
|---|---|---|---|
| 流动比率 X4 | >20.09 | 是 | B4（风险数字=1） |
| 速动比率 X5 | >20.09 | 是 | B5（风险数字=5） |
| 利润总额增长率 X7 | >20.09 | 是 | B7（风险数字=1） |
| 固定资产周转率 X11 | >20.09 | 是 | B11（风险数字=1） |
| 总资产周转率 X12 | >20.09 | 是 | B12（风险数字=5） |
| 资产报酬率 X2 | M>20 | 是 | M2 |
| 速动比率 X5 | M>20 | 是 | M5 |
| 利润总额增长率 X7 | M>20 | 是 | M7 |
| 总资产现金回收率 X15 | M>20 | 是 | M15 |

> 杨贵军等实证结论：包含"评选指标"Benford 因子 B1' 和 Myer 因子 M1' 的 BM-BP 模型，预测准确率 0.8441，二类误判率 0.1623，均为 9 个模型中最优。

### 2-A.5 第二层详解：财务健康判别核心（基于马秀颖等，2026）

**核心思想**：传统判别分析（如 Fisher、Logistic）存在四个缺陷：① 未考虑规模收益不变/可变；② 未区分指标性质（正指标 vs 逆指标）；③ 未考虑投入产出关系；④ 未考虑指标间交互。改进 DEA-DA 逐一解决。

**具体实现**：

**Step 1：指标筛选（决策树）**

先用决策树计算 15 个财务比率的信息增益，筛选重要性最高的 7 个：

| 排序 | 指标 | 符号 | 类型 |
|---|---|---|---|
| 1 | 营业利润率 | X3 | 正指标 |
| 2 | 利息保障倍数 | X6 | 正指标 |
| 3 | 资产报酬率 | X2 | 正指标 |
| 4 | 净资产收益率 | X1 | 正指标 |
| 5 | 总资产增长率 | X9 | 正指标 |
| 6 | 利润总额增长率 | X7 | 正指标 |
| 7 | 速动比率 | X5 | 正指标 |

**Step 2：指标性质标注**

| 指标 | 性质 | 经济含义 |
|---|---|---|
| X1~X3（盈利能力） | 正指标 | 越大越好 |
| X5（速动比率） | 正指标 | 越大越好 |
| X6（利息保障倍数） | 正指标 | 越大越好 |
| X7、X9（成长能力） | 正指标 | 越大越好 |

> 所有 7 个指标均为正指标。若存在逆指标（如资产负债率），需在前处理时取倒数转换。

**Step 3：投入产出配对**

按 DEA 逻辑，将 7 个指标分为"投入"和"产出"两组：

| 投入指标 | 产出指标 |
|---|---|
| 总资产增长率 X9（资产扩张投入） | 净资产收益率 X1（股东回报产出） |
| 利润总额增长率 X7（利润增长投入） | 资产报酬率 X2（资产效率产出） |
| 应收账款周转天数（资金占用投入） | 营业利润率 X3（盈利效率产出） |
| 资产负债率（财务杠杆投入） | 利息保障倍数 X6（偿债能力产出） |

**Step 4：DEA-DA 两阶段判别**

**阶段一（分类+识别重叠）**：

```
min J = Σ sᵢ⁺ + Σ sⱼ⁻          （两类判别误差加权总和最小化）
s.t.
  ΣvᵢXᵢⱼ + ΣuᵣYᵣⱼ + sᵢ⁺ = d,  j∈G₁   （组1判别约束）
  ΣvᵢXᵢⱼ + ΣuᵣYᵣⱼ - sⱼ⁻ = d,  j∈G₂   （组2判别约束）
  Σvᵢ + Σuᵣ = 1,  vᵢ>0, uᵣ>0, d无约束
```

其中 vᵢ、uᵣ 为投入/产出指标权重，s⁺、s⁻ 为判别误差（松弛变量），d 为判别临界值。

**阶段二（处理重叠部分）**：

对阶段一未能完全分离的重叠区域 C，引入判别临界值 c，二次判别：

```
min Σs⁺ + Σs⁻
s.t.
  ΣvᵢXᵢⱼ + ΣuᵣYᵣⱼ + s⁺ = c,  j∈C₁
  ΣvᵢXᵢⱼ + ΣuᵣYᵣⱼ - s⁻ = c,  j∈C₂
  c₁ ≤ c ≤ c₂
```

**Step 5：规模收益处理**

采用 BCC 模型（规模收益可变），避免"大企业天然得分高"的规模偏差：

- 若 Σvᵢ + Σuᵣ = 1（不变规模收益 CRS）→ 使用 CRS 权重
- 若 Σvᵢ + Σuᵣ ≠ 1（可变规模收益 VRS）→ 引入凸性约束，使用 VRS 权重

**千问表格落地方式**：

由于千问表格公式引擎无法直接求解线性规划，本层采用**混合实现**：

1. **系数表**：在千问表格中建立 `deada_coefficients` 表，存储预计算好的指标权重 vᵢ 和 uᵣ（通过 Python scipy 离线求解后导入）
2. **判别计算**：用 SUMPRODUCT 公式计算判别得分 `D = Σvᵢ×Xᵢ + Σuᵣ×Yᵣ`
3. **临界值判定**：`IF(D < d_threshold, "财务风险", "正常")`
4. **动态更新**：每月定时任务中，Agent 调用 MCP 读取最新财务数据，Python 端重新求解线性规划，更新 `deada_coefficients` 表

**实证依据**（马秀颖等，2026）：

| 方法 | 非ST类查全率（均值） | ST类查全率（均值） |
|---|---|---|
| 改进DEA-DA（投入产出+规模收益可变） | 94.17%（2021年最高） | 63.33% |
| 传统L1-SVM | 63.32%~91.43% | 15%~66% |
| 传统L2-SVM | 75.72%~77.51% | 41.97%~63.67% |

> 改进 DEA-DA 在 ST 类（少数类，误判代价最高）查全率显著优于 SVM，且权重具有稀疏性，便于解释"哪几个指标决定了判别结果"。

### 2-A.6 第三层详解：异常样本复核（基于孙玲莉等，2021）

**核心思想**：第二层的判别结果可能存在误判（I类/II类错误）。对判定为"风险"的样本，用 Benford-随机森林 做二次复核——既利用了 Benford 因子提供的"数据质量线索"，又利用随机森林的集成优势降低过拟合。

**具体实现**：

**Step 1：构造 Benford 因子**

与 2-A.4 相同，对每个财务指标的 15 个变量构造 Benford 因子 Bⱼ。

**Step 2：构建随机森林**

```
输入特征 = [X₁, X₂, ..., X₁₅, B₁, B₂, ..., B₁₅]   （30维）
输出标签 = Y ∈ {0, 1}  （0=正常, 1=ST/风险）
```

随机森林参数：
- 决策树数量 n_estimators = 100~200（通过学习曲线调优）
- Bootstrap 重抽样保证样本差异性
- 最终分类：多数投票 `H(X_B) = argmax Σ I(hₛ(X_B⁽ˢ⁾) = Y)`

**Step 3：复核逻辑**

| 第二层结果 | 第三层复核概率 P | 最终判定 |
|---|---|---|
| 正常（D ≥ 0） | — | **绿灯**（无需复核） |
| 风险（D < 0） | P ≥ 0.7 | **红灯 + 疑似粉饰**（升级） |
| 风险（D < 0） | 0.3 ≤ P < 0.7 | **黄灯**（经营性问题） |
| 风险（D < 0） | P < 0.3 | **黄灯**（降级，排除粉饰） |

**千问表格落地方式**：

1. 随机森林模型用 Python（scikit-learn）离线训练，导出为 PMML 或 ONNX 格式
2. 每月定时任务中，Agent 调用 MCP 的 `random_forest_predict(features)` 工具获取 P 值
3. 千问表格根据返回的 P 值做最终判定

**实证依据**（孙玲莉等，2021）：

> 孙玲莉等使用 2000-2018 年中国 A 股非金融业上市公司数据（184 家 ST + 184 家配对正常公司，共 368 家），对比 RFB（带 Benford 因子）与 RF（不带因子）的预测准确率。结论：Benford 因子能够识别存在财务舞弊的具体样本点并提供数据质量信息，带 Benford 因子的随机森林模型准确率更高。

### 2-A.7 三层模型的输出融合

最终预警等级由三层输出共同决定。原先用「或」连接条件的写法存在规则重叠、
结果依赖书写顺序、空值与上游降级未定义等问题（详见
`docs/融合规则口径冲突消歧报告_20261028.md`），此处改写为**互斥且完备**的决策表。

**第一步：术语统一与状态离散化**

三个输入先离散化为有序状态，规则只针对状态书写，从而消除
「区间边界怎么算」「两个阈值之间算什么」这类歧义。区间一律**左闭右开**。

| 维度 | 状态 | 判定式 | 说明 |
|---|---|---|---|
| Q | 缺失 | 空值 / 非数值 / 越界 | 含 NaN、±Inf、字符串、布尔 |
| Q | 严重不足 | Q < 0.3 | |
| Q | 存疑 | 0.3 ≤ Q < 0.5 | |
| Q | 达标 | Q ≥ 0.5 | 绿灯门槛 |
| D | 缺失 | 空值 / 非数值 / **上游求解降级** | DEA-DA 未收敛时得分不可信 |
| D | 风险 | D < 0 | |
| D | 正常 | D ≥ 0 | |
| P | 缺失 | 空值 / 非数值 / 越界 / **树数=0** | 随机森林未训练出树时 P 无意义 |
| P | 高 | P ≥ 0.7 | 阈值符号统一为 ≥ |
| P | 中 | 0.3 ≤ P < 0.7 | |
| P | 低 | P < 0.3 | 排除粉饰 |

**来源优先级**：Q > D > P。数据不可信时，后两层建立在数据之上的结论失去基础，
这是 2-A.3「前一层的输出是后一层的输入」的直接推论。

**第二步：决策表（48 种状态组合，一一映射，无重叠、无空洞、无兜底）**

| 规则 | Q 状态 | D 状态 | P 状态 | 等级 | 依据 |
|---|---|---|---|---|---|
| FUSE-R1 | 缺失 | 任意 | 任意 | 红灯 | 第一层门禁失效，无法支撑任何结论 |
| FUSE-R2 | 严重不足 | 任意 | 任意 | 红灯 | Q<0.3 数据质量严重不足 |
| FUSE-R3 | 存疑 / 达标 | 缺失 | 任意 | 黄灯 | 第二层判别得分不可用，无法判定健康 |
| FUSE-R4 | 存疑 / 达标 | 风险 | 高 | 红灯 | 判为风险且 P≥0.7，风险叠加疑似粉饰 |
| FUSE-R5 | 存疑 / 达标 | 风险 | 中 / 低 / 缺失 | 黄灯 | 判为风险；依据按 P 细分（降级 / 灰区 / 未复核） |
| FUSE-R6 | 存疑 / 达标 | 正常 | 高 | 黄灯 | D≥0 但 P≥0.7，结论冲突，不放行绿灯 |
| FUSE-R7 | 存疑 | 正常 | 中 / 低 | 黄灯 | 数据质量 0.3≤Q<0.5 未达绿灯门槛 |
| FUSE-R8 | 存疑 | 正常 | 缺失 | 黄灯 | 质量未达门槛且第三层未复核 |
| FUSE-R9 | 达标 | 正常 | 缺失 | 黄灯 | 第三层复核不可用，证据链不完整 |
| FUSE-R10 | 达标 | 正常 | 中 / 低 | 绿灯 | 三层证据一致支持健康 |

组合数校验：4×3×4 = 48，上表各行组合数之和 = 12+12+8+2+6+2+2+1+1+2 = 48。

**等价的紧凑表述**（仅供速览，**不用于实现**；实现以决策表为准）：

```
红灯：Q不可用，或 Q<0.3，或 (D<0 且 P≥0.7)
黄灯：D不可用，或 (D<0 且 P<0.7)，或 (D≥0 且 P≥0.7)，或 (D≥0 且 Q<0.5)，或 (D≥0 且 Q≥0.5 且 P不可用)
绿灯：Q≥0.5 且 D≥0 且 P<0.7
```

**与旧口径的对比**：红灯条件（Q<0.3，或 D<0 且 P≥0.7）**完全不变**。
唯一的变化是 FUSE-R6：原先 `D≥0 且 Q≥0.5` 无条件判绿灯，导致 P=0.98 的样本
也会被判「绿灯 · 不触发动作」，第三层输出在融合中等同于死代码。
现改为「两个结论冲突 → 黄灯，转人工复核」。

**可视化（三色灯逻辑）**：

| 条件 | 显示 | 触发动作 |
|---|---|---|
| 红灯 | 红色背景 | Agent 拉群、@财务总监+总经理、24h内响应 |
| 黄灯 | 黄色背景 | Agent @部门经理、48h内提交方案 |
| 绿灯 | 绿色背景 | 仅记录，不触发动作 |

### 2-A.8 学术引用与答辩话术

**答辩时引用方式**：

> "我们的预警模型不是凭经验拍脑袋定的。第一层数据质量门禁引用杨贵军等 2022 年发表于《统计与决策》的 BM-BP 模型，用 Benford 律和 Myer 指数双因子检验数据质量；第二层财务健康判别核心引用马秀颖等 2026 年发表于《数理统计与管理》的改进 DEA-DA 模型，兼顾规模收益和投入产出比；第三层异常复核引用孙玲莉等 2021 年发表于《数量经济技术经济研究》的 Benford-随机森林模型。三层各有实证支撑，融合后互补短长。"

### 模块三：风控闸（红黄绿判定 + 动态阈值 + 常态化压力测试）

#### 4.0 三层风控模型判定（v8 新增，替代 v7 的单一缓冲阈值判定）

> **v8 核心升级**：v7 的预警判定逻辑是「现金缓冲 < 行业阈值 → 黄灯/红灯」，属于单一维度的规则判定。v8 引入三层模型，判定逻辑升级为「FUSE(Q, D, P) → 绿灯/黄灯/红灯」，融合了数据质量、财务健康、舞弊识别三个维度。

**判定流程**：

```
财务比率指标（15个）
    ↓
┌─────────────────────────────────────────┐
│ 第一层：数据质量门禁                      │
│ • Benford律首位数字χ²检验                │
│ • Myer指数末位数字检验                   │
│ • 构造Bₖ、Mₖ质量因子                    │
│ • 输出：数据质量得分 Q ∈ [0, 1]          │
└────────────────┬────────────────────────┘
                 ↓
┌─────────────────────────────────────────┐
│ 第二层：财务健康判别（改进DEA-DA）        │
│ • 7个核心指标（决策树筛选）               │
│ • 指标性质标注（正/逆指标）               │
│ • 投入产出配对                           │
│ • BCC规模收益可变                        │
│ • 输出：判别得分 D ∈ [-1, 1]             │
└────────────────┬────────────────────────┘
                 ↓
         D < 0（判定为风险）
                 ↓
┌─────────────────────────────────────────┐
│ 第三层：异常样本复核（Benford-随机森林）  │
│ • 30维特征（15财务指标 + 15 Benford因子） │
│ • Bootstrap重抽样 + 多数投票             │
│ • 输出：舞弊概率 P ∈ [0, 1]              │
└────────────────┬────────────────────────┘
                 ↓
        融合判定 FUSE(Q, D, P)
                 ↓
        ┌────────┼────────┐
       绿灯     黄灯      红灯
```

**融合判定公式**（权威版本为 2-A.7 的十行决策表，此处为速览表述）：

```
FUSE(Q, D, P) =
    红灯：Q不可用，或 Q<0.3，或 (D<0 且 P≥0.7)
    黄灯：D不可用，或 (D<0 且 P<0.7)，或 (D≥0 且 P≥0.7)，
          或 (D≥0 且 Q<0.5)，或 (D≥0 且 Q≥0.5 且 P不可用)
    绿灯：Q≥0.5 且 D≥0 且 P<0.7
```

**算法等价表达（v8.2：以下公式仅用于说明规则，实际由后端代码实现）**：

```excel
# 第一层：数据质量得分
数据质量得分Q = 1 - (SUMPRODUCT(Benford因子范围) + SUMPRODUCT(Myer因子范围)) / (2 × 15)

# 第二层：DEA-DA判别得分
判别得分D = SUMPRODUCT(投入指标权重, 投入指标) + SUMPRODUCT(产出指标权重, 产出指标)

# 第三层：随机森林舞弊概率（通过MCP调用Python计算）
舞弊概率P = MCP_CALL("rf_predict", 特征向量)

# 融合判定（示意；权威实现为决策表，见 2-A.7）
# 旧写法 IF(OR(...), "红灯", IF(OR(...), "黄灯", "绿灯")) 已被替换：
#   - 旧写的两个「或」条件存在交集，结果依赖嵌套顺序；
#   - 旧写没有兜底之外的空值处理，且任何未覆盖情形都落到最后的"绿灯"，
#     等于把「没算出来」当成「健康」。
# 新写法逐条件互斥，且显式处理缺失：
IF(Q不可用, "红灯",
IF(Q<0.3, "红灯",
IF(D不可用, "黄灯",
IF(AND(D<0, P>=0.7), "红灯",
IF(D<0, "黄灯",
IF(P不可用, "黄灯",
IF(P>=0.7, "黄灯",
IF(Q<0.5, "黄灯", "绿灯"))))))))
```

**与 v7 的关系**：v7 的「缓冲阈值判定」并未废弃，而是降级为「第二层的辅助约束」——DEA-DA 的判别得分 D 同时会参考现金缓冲是否低于 M×K红（相对阈值）。两层逻辑并行，最终结果取较严格者。

#### 4.1 静态阈值（默认，数据不足 12 个月时强制使用）

> 静态阈值的取值见第五章"阈值来源表"，每一项都标注出处、年份与样本量。

| 维度 | 规则（v8 相对指标口径） |
|---|---|
| 三级预警线 | 现金缓冲 < M×K红 → 红灯；< M×K黄 → 黄灯（M=月均经营性流出，K=行业系数） |
| 相对阈值 | 应收账款周转天数/行业均值 > 1.3 → 关注；> 1.5 → 黄灯 |
| 相对阈值 | 存货周转天数/行业均值 > 1.3 → 关注；> 1.5 → 黄灯 |
| 相对阈值 | 流动比率/行业基准 < 0.7 → 黄灯；< 0.5 → 红灯 |
| 数据质量门禁 | Benford χ² > 20.09 或 Myer 指数 > 20 → 标记数据质量风险 |
| 财务健康判别 | DEA-DA 判别得分 D < 0 → 标记财务风险 |
| 舞弊复核 | Benford-随机森林：P ≥ 0.7 且 D<0 → 升级红灯；P ≥ 0.7 且 D≥0 → 黄灯（结论冲突，转人工复核，不放行绿灯）；P < 0.3 → 降级黄灯（仅经营性问题）。**P 不可单独定级**，须与 D 联合判定，详见 2-A.7 |
| 四种模拟场景 | 回款冲击 / 成本冲击 / 双重冲击 / 联合冲击 |
| 假设分析 | 用户输入参数，Agent 调用表格重算 |
| 复合规则 | 如"回款延期>30天 且 融资缓冲<M×K黄 → 红灯" |
| 归因分析 | 触发预警后自动分析主因及贡献度（含DEA-DA权重解读） |

#### 4.2 动态阈值（数据满 12 个月才启用）

**问题**：固定阈值在旺季容易误报、淡季容易漏报。

**启用条件（v7 修正，逻辑统一）**：

| 历史数据量 | 使用方式 |
|---|---|
| **不足 12 个月** | **强制使用静态阈值**，不使用任何分位数 |
| **满 12 个月及以上** | 可申请开启动态阈值，用滚动分位数计算预警线 |

> 修正说明：v6 同时写了"滚动 12 个月"和"满 6 个月启用"，两者矛盾。6 个月只有 6 个同月数据点，百分位极不稳定，故统一改为 12 个月。
> **v8.2 修订**：分位数**由后端脚本计算**，不再依赖平台 `PERCENTILE` 函数，该依赖已彻底解除。

**算法等价表达（v8.2：以下公式仅用于说明规则，实际由后端代码实现）**：

```excel
# 步骤1：计算月均经营性流出 M（近3个月平均）
M = AVERAGE(近3月经营性流出)

# 步骤2：取过去12个月同期（同月）的"缓冲倍数"（缓冲÷M）
同期缓冲倍数 = FILTER(历史数据!缓冲列/历史数据!M列, MONTH(历史数据!日期列)=MONTH(TODAY()))

# 步骤3：计算第25百分位作为黄灯倍数
K黄 = PERCENTILE(同期缓冲倍数, 0.25)

# 步骤4：计算第10百分位作为红灯倍数
K红 = PERCENTILE(同期缓冲倍数, 0.10)

# 步骤5：计算实际缓冲倍数
实际缓冲倍数 = 当前缓冲 / M

# 步骤6：判定（相对口径）
IF(实际缓冲倍数 < K红, "红灯",
   IF(实际缓冲倍数 < K黄, "黄灯", "绿灯"))
```

> **关键区别**：v7 的判定是「当前缓冲 < 红灯线（绝对金额）」，v8 改为「当前缓冲÷M < K红（相对倍数）」。前者随企业规模变化需要手动调整阈值，后者自动适应任何规模。

**逻辑说明**：
- 第25百分位：当前缓冲低于过去12个月同期的后25%时触发黄灯
- 第10百分位：低于过去12个月同期的后10%时触发红灯
- 旺季时（去年同期数据本身就高），阈值自动抬高，避免误报
- 淡季时（去年同期数据本身就低），阈值自动降低，避免漏报

**配置面板增加"动态阈值开关"**：

| 开关状态 | 行为 | 前置条件 |
|---|---|---|
| 关闭 | 使用行业静态参数作为预警线 | 无 |
| 开启 | 使用滚动分位数动态计算预警线 | 数据满 12 个月 |
| 混合模式 | 静态阈值 × 0.7 + 动态阈值 × 0.3（平滑过渡） | 数据满 12 个月 |

**启用校验**：若历史数据不足 12 个月却强行开启动态阈值，配置面板应给出提示并自动回退到静态阈值。

#### 4.3 常态化压力测试模块（唯一主述位置）

**问题**：压力测试应该是定期跑的，而不是每次新业务申请才跑。

**解决方案**：设置定时任务，每月1号凌晨自动跑一次全量压力测试。

**执行流程**：

```
每月1号 00:30 定时任务触发
    ↓

    ↓
自动执行四种模拟场景：
    场景1：回款冲击（所有应收延迟30天）
    场景2：融资冲击（授信额度缩减50%）
    场景3：成本冲击（主要成本上涨20%）
    场景4：联合冲击（以上三项同时发生）
    ↓
每种场景下计算：
    最坏情况现金缓冲

    ↓

    ↓

    ↓
```

```markdown

## 当前状态
- 现金缓冲：185万（= 月均流出M 100万 × 缓冲倍数 1.85 → 黄灯）
- 缓冲倍数：1.85（K黄=2.5，K红=1.5，介于两者之间）
- 时间缓冲：32天
- 融资缓冲：120万可用

## 压力测试结果（v8 相对指标口径）
| 场景 | 最坏情况缓冲 | 缓冲倍数 | 缓冲剩余天数 | 风险等级 |
|---|---|---|---|---|
| 回款冲击（应收延迟30天） | 120万 | 1.20 | 18天 | 黄灯（1.20<K黄） |
| 融资冲击（授信缩减50%） | 65万 | 0.65 | 8天 | 红灯（0.65<K红） |

| 联合冲击（三项同时） | -15万 | -0.15 | 0天 | 红灯（负数） |

- 联合冲击下缓冲倍数为负，主要风险来自融资额度不足

1. 短期：催收A客户欠款（预计回款45万，15天内到账 → 缓冲倍数恢复至1.65）
2. 中期：启用备用授信额度（预计释放60万 → 缓冲倍数恢复至2.25，回到绿灯区间）
3. 长期：拓展融资渠道，降低单一银行依赖
```

**千问表格公式（场景模拟，v8 相对指标口径）**：

```excel
# 月均经营性流出 M
M = AVERAGE(近3月经营性流出)

# 回款冲击：所有应收延迟30天（缺口 = 30天内到期应收金额）
回款冲击缺口 = SUMIF(应收账款!到期日, "<="&TODAY()+30, 应收账款!金额)
回款冲击后缓冲倍数 = (当前缓冲 - 回款冲击缺口) / M

# 融资冲击：授信额度缩减50%
融资冲击缺口 = 可用授信额度 × 0.5
融资冲击后缓冲倍数 = (当前缓冲 - 融资冲击缺口) / M

# 成本冲击：主要成本上涨20%
成本冲击缺口 = 月度主要成本 × 0.2
成本冲击后缓冲倍数 = (当前缓冲 - 成本冲击缺口) / M

# 联合冲击：三项同时发生
联合冲击缺口 = 回款冲击缺口 + 融资冲击缺口 + 成本冲击缺口
联合冲击后缓冲倍数 = (当前缓冲 - 联合冲击缺口) / M

# 场景判定
IF(场景缓冲倍数 < K红, "红灯", IF(场景缓冲倍数 < K黄, "黄灯", "绿灯"))
```

#### 4.2 例外审批回溯机制

**千问表格公式（例外率统计）**：

```excel

```

#### 5.2 到账验证子模块

**问题**："到账（实际入账）"这个状态怎么确认？如果是手工填报，存在虚报风险。

**解决方案**：提供三种方式，用户根据自身条件选择。

**方式一：银企直连自动对账（推荐）**

通过千问办公连接器接入银行 API，自动比对到账金额和应收金额：

```excel
# 自动对账公式
IF(银行流水!到账金额 = 应收账款!应收金额, "已验证到账", "金额不符")
IF(银行流水!到账日期 <= 应收账款!到期日 + 3, "按时到账", "延期到账")
```

**方式二：到账凭证上传 + 抽检（低成本方案）**

- 责任人上传到账凭证（银行截图或 PDF）
- 系统在上传的凭证中**随机抽取 20%** 进行人工复核
- 复核方式：与银行流水或原始单据比对
- 抽检发现问题 → 标记该部门为"高风险" → 触发审计检查

**方式三：待验证状态（最低保障）**

- 不具备以上两种方式时，到账标记为"待验证"
- "待验证"状态的金额**不计入现金缓冲计算**
- 只有验证通过后，才纳入缓冲计算

**验证状态流转**：

```
待验证（手工填报或上传凭证）
    ↓
方式一：银企直连 → 自动验证通过/失败
方式二：凭证上传 → 随机抽检 → 通过/退回重传
    ↓
验证通过 → 计入现金缓冲 → 三态跟踪更新为"已化解"
验证失败 → 标记异常 → 通知责任人 → 重新提交
```

**千问表格公式**：

```excel
# 到账状态判定
IF(验证方式="银企直连",
    IF(银行流水匹配, "已验证", "验证失败"),
    IF(AND(验证方式="凭证上传", 抽检结果="通过"),
        "已验证",
        IF(抽检结果="失败", "验证失败", "待验证")
    )
)

# 现金缓冲只计入已验证到账
有效缓冲 = SUMIF(到账状态列, "已验证", 金额列)
```

> **v8.2 范围收窄**：钉钉与企业微信在本方案中**只做消息推送，不做建群 / @成员**，该项已从能力清单中移除，不再存在"降级"问题。闭环动作改为："后端计算并判定 → MCP 触发推送 → 接收人在原系统内处理 → 状态变更写回数据库"，闭环验证以**任务状态是否变更**为判据（与是否建群无关）。待办清单由后端生成并随消息一并推送。

**闭环流程图**：

```
触发条件
    ↓
Agent 执行动作（拉群/@/建任务）
    ↓
责任人收到通知，执行动作
    ↓
Agent 持续跟踪任务状态
    ↓
是否完成？ ──否──→ 到期未关闭 → 自动升级通知
    │
    └─是──→ 验证结果是否符合预期？
                │
            ┌───┴───┐
           否       是
            ↓       ↓
      重新评估   标记为闭环
      原因      写入审计日志
```

**关键原则**：Agent 的每一个"推动"动作都有对应的"验证"机制，确保闭环真实有效。

>
> **现金缓冲黄灯线 = 月均经营性流出 M × K黄**
> **现金缓冲红灯线 = 月均经营性流出 M × K红**

## 六、参数自修正机制

### 6.1 核心思路

固定参数是起点，目标是让系统根据实际使用情况递推修正，向"企业专属"方向演进。

```
预设参数 → 系统运行 → 产生预警 → 记录实际偏差 → 修正参数 → 再运行
```

每一次预警、审批、推演都在提供反馈信号，系统据此校准参数。

> **v7 重要修正**：以下机制描述的是**设计逻辑与预期方向**，参数能否收敛、准确率能否提升，**取决于实际运行数据，方案不预设量化效果**。"三个月提升 15%~25%"这类数字已从本方案中删除。

### 6.2 实现步骤（千问表格公式 + Agent）

**第一步：记录每次预警的实际结果**

在审计日志表里增加 `feedback_log` 表：

| 字段 | 说明 |
|---|---|
| event_type | 预警类型 |
| predicted_value | 预警时的预测值 |
| actual_value | 实际结果值 |
| accuracy | 准确 / 误报 / 漏报 |
| deviation | 偏差幅度 |
| created_at | 记录时间 |

> **标注方式说明**：`accuracy` 字段的值（准确/误报/漏报）需要有人对比预警结果与实际经营情况后人工标注。这是一项必须计入的工作成本，不能隐含为"自动完成"。方案建议由财务负责人按月复核标注，或委托参赛队包 B 在测试期代为模拟标注。

**第二步：Agent 定期统计偏差率**

定时任务每月1号执行：

- 黄灯准确率 = 黄灯触发后真正出问题的次数 ÷ 黄灯总触发次数
- 红灯准确率 = 红灯触发后真正出问题的次数 ÷ 红灯总触发次数
- 平均偏差幅度 = 预警值与实际临界值的差距均值

**第三步：根据偏差修正参数**

修正规则（写在千问表格公式或 Agent 提示词里）：

| 情况 | 修正动作 | 修正幅度 |
|---|---|---|
| 黄灯准确率偏低（误报多） | 黄灯线下调 | -10% |
| 红灯准确率偏低（漏报多） | 红灯线上调 | +10% |
| 平均偏差幅度偏大（整体不准） | 所有参数乘修正系数 | ±5% |
| 连续多次准确 | 保持当前参数 | 0% |

**示例**：制造业现金缓冲黄灯线初始 200 万，连续两个月实际证明 185 万更接近真实危险线，系统修正为 185 万。

### 6.3 修正公式

```
新参数 = 旧参数 × (1 + 修正系数)

修正系数 = (实际平均临界值 - 当前参数值) / 当前参数值

约束：单次修正幅度不超过 ±15%，累计修正不超过 ±30%
```

#### 6.7.2 三层模型的创新性表述

**创新点一：数据质量前置检验（Benford + Myer 双因子）**

传统财务风险预警模型直接使用企业提供的财务数据作为输入，假设数据真实可靠。但杨贵军等（2022）的实证研究表明，**ST 公司的财务数据首位数字分布显著偏离 Benford 律**，说明粉饰行为会系统性扭曲预警模型的输入。本方案在数据处理环节引入 Benford 律和 Myer 指数双质量因子，在数据进入计算前先做可信度检验，从根源上降低了"垃圾进、垃圾出"的风险。

**创新点二：判别模型的可解释性增强（改进 DEA-DA）**

传统机器学习模型（神经网络、随机森林）存在"黑箱"问题，决策者和投资者无法理解判定依据。马秀颖等（2026）的改进 DEA-DA 模型通过线性规划求解指标权重，权重具有稀疏性——**只有少数关键指标的权重非零，这些指标即为核心判别因子**。本方案沿用这一思路，在配置面板中展示判别得分的构成（哪些指标贡献了多少），使判定过程透明可解释。

**创新点三：串行融合而非简单叠加**

三篇文献各自提出了独立的预警模型。本方案不是简单地将三个模型的结果取平均，而是设计了**串行融合架构**：

- 第一层（数据质量）的输出 Q 是第二层（健康判别）的**输入权重**——数据质量越差，第二层的判别得分置信度越低
- 第二层（健康判别）的输出 D 是第三层（随机森林）的**输入特征**——D 值越接近临界，第三层的复核权重越高
- 第三层的输出 P 是最终预警等级的**修正因子**——P 值越高，越倾向于升级为红灯

这种融合方式避免了"三个模型独立运行、结果可能互相矛盾"的问题，形成了完整的证据链。

## 七、自适应深度模型与普适性设计

### 7.1 核心思想：不问行业，只问事实

传统做法：先预设行业，再给参数 → 换行业就要重新配置，普适性差。

本方案做法：**不给死参数，给一套"认识行业"的工具。** 任何行业、任何规模的企业进来，系统通过引导式问答自动生成适配参数。

**理论依据**：企业财务风险的本质结构是相同的（现金流入、现金流出、缓冲空间），差异只在于各要素的权重和周期。因此只需了解企业的实际经营特征，就能自动推导参数。

### 7.2 第一步：行业画像引导式问卷

用户首次使用时，Agent 弹出 5 个引导式问题，**用户不需要知道自己是哪个行业，只需如实回答企业经营情况**：

| 问题 | 选项 | 对应推导参数 |
|---|---|---|
| 1. 你的主营业务是什么？ | 产品制造 / 商品销售 / 工程项目 / 技术服务 / 其他 | 确定核心商业模式 → 现金流结构 |
| 2. 你的主要成本是什么？ | 原材料 / 采购成本 / 人力成本 / 设备折旧 / 外包费用 | 确定现金流出结构 → 缓冲权重 |
| 3. 你的回款周期大概是多久？ | 即时 / 15天以内 / 15~60天 / 60天以上 / 按项目进度 | 确定时间缓冲基线 |
| 4. 你的资金来源主要是？ | 自有资金 / 银行贷款 / 股权融资 / 政府补贴 / 预收款 | 确定融资缓冲权重 |
| 5. 你的业务有没有明显淡旺季？ | 没有 / 有（集中在某几个月） | 确定季节性调整系数 |

**5 个问题 × 各 5 个选项，理论上可形成 3125 种组合，覆盖多行业 × 多场景的组合空间。**

> v7 表述修正：3125 是理论组合数，不代表已经实测覆盖 3125 种企业类型。参赛阶段以四个行业模板（制造业、零售业、建筑业、科技服务业）为已验证样板，其余组合作为可扩展的映射框架，不宣称"覆盖绝大多数企业"。

系统根据用户答案自动匹配到最接近的预设模板，并在此基础上做微调：

| 答案组合示例 | 匹配模板 | 微调方向 |
|---|---|---|
| 产品制造 + 原材料 + 60天 + 银行贷款 + 有淡旺季 | 制造业 | 加入季节性系数 |
| 商品销售 + 采购成本 + 即时 + 自有资金 + 有淡旺季 | 零售业 | 融资缓冲降为10% |
| 技术服务 + 人力成本 + 15天 + 股权融资 + 无淡旺季 | 科技服务业 | 人力成本权重提升 |
| 工程项目 + 外包费用 + 按进度 + 预收款 + 无淡旺季 | 建筑业 | 增加预收款抵扣项 |

### 7.3 第二步：深度四层穿透

**深度的本质不是功能多，而是能一层层追问下去，直达根因。**

```
第一层：发生了什么？（预警）
    例：现金缓冲低于黄灯线

第二层：为什么会发生？（归因）
    例：回款延迟 + 集中采购，其中回款延迟贡献65%

第三层：接下来会发生什么？（推演）
    例：催收15天恢复 / 贷款3天恢复但要付2万利息

第四层：以后怎么避免？（根因追踪）
    例：最大客户改变了付款习惯，建议与该客户协商缩短账期
```

| 层级 | 在千问办公中的实现 | Agent 回复示例 |
|---|---|---|
| 第一层（预警） | 千问表格条件格式自动标色 | "当前现金缓冲为185万，低于200万黄灯线" |
| 第二层（归因） | Agent 自动读取表格，分析各因素贡献度 | "主要原因是A客户回款延期18天（贡献65%），其次是集中采购（贡献35%）" |
| 第三层（推演） | Agent 调用表格模拟，多方案卡片对比 | "方案A：催收 → 15天恢复，零成本；方案B：启用授信 → 3天恢复，利息2万" |
| 第四层（根因） | Agent 结合历史趋势，识别长期变化 | "应收账款账期从45天延长到57天，是因为A客户自2025Q4起改变了付款政策，建议协商缩短账期" |

**用户全程只需提问，四层穿透由 Agent 自动完成。**

### 7.4 第三步：运行后自动修正

沿用第六章的参数自修正机制：

- 系统运行 → 产生预警 → 记录实际结果 → 统计准确率 → 修正参数
- 参数向"企业专属"方向演进（演进速度取决于实际数据）

### 7.5 第四步：跨企业经验迁移

**这是普适性的最高形态：每一个企业的使用经验，都在让整个系统变得更聪明。**

每季度定时任务执行"深度复盘"：

1. 收集所有使用本系统的企业的参数修正记录
2. 按行业聚类，发现共性规律
3. 更新行业参数模板库
4. 通知所有使用该模板的企业："行业基准已更新，是否同步？"

**示例**：
- 10 家制造业企业都修正了存货周转天数基准（从90天调整到95天）
- 系统自动更新制造业模板的默认值
- 新进入的制造业企业直接获得更精准的初始参数
- 从"第一个企业适配较慢"到"第 N 个企业适配更快"

> v7 修正：跨企业迁移的是**参数模板**（聚合后的统计规律），不迁移任何单家企业的原始数据，从源头规避数据泄露风险。模板更新是否采纳由企业自主选择，不强制覆盖。

### 7.6 完整自适应闭环

```
新企业进入
    ↓
回答5个引导式问题 → 系统自动匹配模板并微调（普适性）
    ↓
系统开始运行 → 产生预警（第一层）
    ↓
Agent 自动归因（第二层）
    ↓
Agent 自动推演（第三层）
    ↓
Agent 追踪根因（第四层）
    ↓
系统根据实际结果修正参数（自修正）
    ↓
参数向"企业专属"演进
    ↓
季度复盘 → 跨企业经验迁移 → 更新行业模板
    ↓
下一个新企业进入（复用模板经验）
```

```python
from fastapi import FastAPI
from pydantic import BaseModel
import mysql.connector
from datetime import datetime

app = FastAPI()

class LogRequest(BaseModel):
    event_type: str
    payload: dict

class FeedbackRequest(BaseModel):
    event_type: str
    predicted_value: float
    actual_value: float
    accuracy: str  # accurate / false_positive / false_negative
    deviation: float

class ParamTemplateRequest(BaseModel):
    industry_key: str
    params: dict
    source: str  # onboarding / self_adjust / quarterly_review

class ExceptionRequest(BaseModel):
    dept: str
    amount: float
    reason: str
    approver: str

class StressTestRequest(BaseModel):
    scenario: str
    result: float
    risk_level: str

class PaymentVerifyRequest(BaseModel):
    payment_id: str
    method: str  # bank_api / voucher / manual
    status: str  # verified / failed / pending

def get_db():
    return mysql.connector.connect(
        host="127.0.0.1", user="audit",
        password="你的密码", database="audit_db"
    )

@app.post("/mcp/log_to_mysql")
def log_to_mysql(req: LogRequest):
    db = get_db()
    cur = db.cursor()
    cur.execute(
        "INSERT INTO audit_log (event_type, payload, created_at) VALUES (%s, %s, %s)",
        (req.event_type, str(req.payload), datetime.now())
    )
    db.commit()
    db.close()
    return {"status": "ok"}

@app.post("/mcp/log_feedback")
def log_feedback(req: FeedbackRequest):
    db = get_db()
    cur = db.cursor()
    cur.execute(
        "INSERT INTO feedback_log (event_type, predicted_value, actual_value, accuracy, deviation, created_at) VALUES (%s, %s, %s, %s, %s, %s)",
        (req.event_type, req.predicted_value, req.actual_value, req.accuracy, req.deviation, datetime.now())
    )
    db.commit()
    db.close()
    return {"status": "ok"}

@app.get("/mcp/query_rule_stats")
def query_rule_stats(rule_id: str = None):
    db = get_db()
    cur = db.cursor()
    if rule_id:
        cur.execute("SELECT event_type, COUNT(*) FROM audit_log WHERE payload LIKE %s GROUP BY event_type", (f"%{rule_id}%",))
    else:
        cur.execute("SELECT event_type, COUNT(*) FROM audit_log GROUP BY event_type")
    result = cur.fetchall()
    db.close()
    return {"stats": result}

@app.get("/mcp/query_feedback_stats")
def query_feedback_stats(event_type: str = None):
    db = get_db()
    cur = db.cursor()
    if event_type:
        cur.execute("SELECT accuracy, COUNT(*), AVG(deviation) FROM feedback_log WHERE event_type=%s GROUP BY accuracy", (event_type,))
    else:
```

## 十三、理论贡献

1. **人机共生**：AI 不替代人决策，而是提供信息、推演方案、锁定责任，人做最终判断。
2. **全链路闭环**：从数据采集 → 清洗 → 计算 → 预警 → 审批 → 跟踪 → 留痕 → 优化，形成完整管理循环。
3. **【v8新增】数据质量前置门禁**：首次将 Benford 律与 Myer 指数双质量因子引入企业现金流风控场景，在数据进入计算前先做可信度检验，从源头降低"垃圾进、垃圾出"风险。区别于传统预警模型直接信任输入数据，本方案将数据质量作为独立的一层风控维度。
4. **【v8新增】改进 DEA-DA 判别模型**：将马秀颖等（2026）的改进 DEA-DA 模型引入企业财务风险判别，兼顾规模收益可变（BCC）、指标性质标注（正/逆指标）、投入产出配对、指标交互，解决了传统判别分析"大企业天然得分高"的规模偏差问题。判别得分通过 SUMPRODUCT 在千问表格中直接计算，权重稀疏可解释。
5. **【v8新增】三层串行融合架构**：不是简单地将三个模型结果取平均，而是设计了串行融合——第一层 Q 值影响第二层置信度，第二层 D 值影响第三层复核权重，第三层 P 值修正最终预警等级。三层各有实证支撑，融合后互补短长。
6. **【v8新增】相对指标阈值体系**：所有预警线从绝对金额改为"月均经营性流出M × 行业系数K"的相对口径，彻底解决企业规模差异导致的阈值失效问题。任何规模企业只需填入自己的月均流出，预警线自动等比缩放。
7. **动态阈值**：基于历史同期滚动分位数动态调整预警线，解决固定阈值在旺季误报、淡季漏报的问题（满12个月数据启用）。v8 进一步将动态阈值改为"缓冲倍数"的相对口径。
8. **普适性设计**：不问行业，只问事实。通过引导式问卷自动生成初始参数（含K系数），覆盖多行业×多场景的组合空间。
9. **参数反馈修正**：系统根据实际使用情况递推修正参数，向"企业专属"方向演进。
10. **深度四层穿透**：预警→归因→推演→根因，从表层现象直达根本原因，不止于亮灯。v8 新增"DEA-DA权重解读"作为归因的量化依据。
11. **跨企业经验迁移**：每季度复盘，将聚合后的参数规律沉淀为行业模板，只迁移模板、不迁移原始数据。v8 新增"DEA-DA系数迁移"——不同企业的判别权重也可作为经验迁移。
12. **Agent 动作闭环**：Agent 不仅"建议"，还能"推动"——自动拉群、@责任人、创建跟进任务、到期升级，每个动作都有验证机制。v8 新增"数据质量分析"和"判别得分解读"两个 Agent 对话分支。
13. **常态化压力测试**：将压力测试从"按需执行"升级为"定期自动执行"，管理层定期看到最坏情况。v8 改为相对缓冲倍数口径。
14. **执行细节与闭环验证矩阵**：明确"谁在什么条件下做什么、做了怎么验证"，使系统从"演示方案"变为"能落地的系统"。
15. **AI 办公平台赋能管理会计**：在千问办公上实现现金流预测、缓冲计算、假设分析、参数自修正、动态阈值、压力测试、Benford/Myer检验、DEA-DA判别等管理会计工具，无需编写传统代码。
16. **平台原生为主 + MCP 外挂**：核心技能全部在平台内完成，MCP 仅作审计留痕和反馈收集工具，符合比赛规则要求（依据 1.4 节所列规则条目）。

| 预警阈值为什么不用绝对金额？ | v8 全部改为相对指标：现金缓冲预警线=月均经营性流出M×行业系数K。原因很简单——企业规模不同，绝对值没有可比性。制造业A月均流出500万，制造业B月均流出80万，用同一套金额门槛必然误报或漏报。改成M×K后，大企业小企业共用同一套逻辑，数值自动缩放 |
| 你怎么保证K系数是对的？ | K黄取行业P25分位、K红取P10分位，来源于上市公司公开财报统计。我们在第五章来源表逐项标注了出处、年份、样本量。不同行业K值不同，因为资金周转特性不同——建筑业K=3.5/2.0（资金需求大），零售业K=1.8/1.0（周转快） |
| 你这个三层模型是不是太复杂了？ | 不复杂。三层是串行调用，不是并行堆叠。第一层Q值正常就跳过第三层；只有第二层判定为风险的样本才进第三层复核。正常企业日常运行只跑第一层+第二层，计算量很小 |
| 为什么选DEA-DA而不是神经网络？ | 两个原因：一是可解释性，DEA-DA求解线性规划，输出的指标权重天然稀疏，只有少数关键指标非零，决策者能看到"哪几个指标决定了判定"；二是马秀颖等2026年的实证显示，在ST类（少数类，误判代价最高）查全率上DEA-DA显著优于SVM和神经网络 |
| Benford律能检测财务舞弊吗？有没有实证？ | 有。Benford律的数学证明由Hill在1995年给出。杨贵军等2022年用2000-2019年A股数据实证，ST公司财务指标的χ²值普遍超过20.09临界值，非ST公司大多通过检验。Myer指数则从末位数字检验，与Benford形成互补 |
| 随机森林的作用是什么？为什么不直接用DEA-DA？ | DEA-DA擅长"健康不健康"的宏观判别，但无法指出"哪条记录有问题"。随机森林配合Benford因子可以定位到具体样本点——哪个指标的哪条记录偏离了Benford分布，这为审计提供了抓手 |
| 三层模型的输出怎么融合？权重怎么定？ | 不是加权平均，是条件融合。D<0且P≥0.7→红灯（确认舞弊）；D<0且P<0.3→黄灯（降级为经营性问题）；Q<0.3直接红灯（数据不可信）。这是基于"证据链"的逻辑判定，不是统计加权 |
| 参数自修正能证明一定收敛吗？ | 目前是设计机制与预期方向，收敛性需真实运行数据验证，方案不预设量化效果 |

## 十八、执行细节与闭环验证矩阵

**本章专门回答评委的终极问题："谁在什么条件下做什么、做了怎么验证？"**

### 18.1 闭环验证总览

| 模块 | 谁执行 | 什么条件 | 做什么 | 怎么验证 |
|---|---|---|---|---|
| 数据闸 | 千问表格公式 | 数据入库时自动 | 缺失填0、去重、格式统一、逻辑校验 | 条件格式标红 + 异常行单独列表 |
| 核心计算 | 千问表格公式 | 数据闸通过后 | 三大现金流预测、缓冲计算、管理会计 | 人工抽检 3~5 行计算结果 |
| 风控闸（静态） | 千问表格公式 | 核心计算完成后 | 与行业参数比对，输出红黄绿 | 条件格式自动标色 |
| 风控闸（动态） | 千问表格公式 + Agent | 数据 ≥ 12 个月且开关开启 | 计算滚动分位数，动态调整预警线 | 对比静态与动态阈值差异，验证旺季不误报、淡季不漏报 |
| 常态化压力测试 | 定时任务 + Agent | 每月1号 00:30 自动触发 | 跑全量四种场景，生成健康度报告 | 报告自动推送到管理层钉钉群；红灯触发紧急会议任务 |
| 分级审批 | Agent + 钉钉 | 风险触发后 | 按级别路由审批人，记录审批结果 | 审批状态写入表格 + MCP 留痕 |
| 例外放行 | Agent + MCP | 审批人选择"例外放行"时 | 记录部门、金额、理由、审批人 | 每季度回溯统计，异常部门触发审计 |
| 例外审批回溯 | 定时任务 + Agent | 每季度1号 06:00 自动触发 | 统计各部门例外率、金额、理由重复率 | 生成回溯报告；异常部门 → 审计检查任务 → 审计报告 |
| 三态跟踪 | 千问表格条件格式 | 审批完成后持续跟踪 | 已化解/观察中/已恶化，倒计时提醒 | 条件格式自动更新；到期未化解自动升级 |
| 到账验证 | Agent + MCP | 责任人标记"到账"时 | 银企直连自动对账 / 凭证上传+抽检 / 待验证 | 验证状态写入 payment_verify_log；失败标记异常 |
| Agent 闭环动作 | Agent + 钉钉 + 表格 | 黄灯/红灯触发时 | 拉群、@责任人、创建跟进任务 | 任务状态从"待处理"→"已完成"才算闭环；到期未关闭自动升级 |
| 参数反馈修正 | 定时任务 + Agent | 每月1号 06:00 自动触发 | 统计准确率，按规则修正参数 | 修正记录写入日志 + 配置面板可见 + 用户可手动覆盖 |
| 跨企业经验迁移 | 定时任务 + Agent | 每季度1号 08:00 自动触发 | 收集参数修正记录，按行业聚类，更新模板 | 新模板通知所有使用该模板的企业；只迁移模板不迁移原始数据 |
| 钉钉推送 | 钉钉连接器 | 各类事件触发时 | 推送预警、日报、报告、@通知 | 推送记录写入 audit_log |
| MCP 留痕 | MCP Server + MySQL | 所有关键事件发生时 | 写入对应日志表 | 可通过 query 工具随时查询验证 |

### 18.2 关键闭环的"验证标准"

每个闭环都必须有明确的"验证通过"标准：

| 闭环 | 验证通过标准 |
|---|---|
| 预警闭环 | 预警触发 → 责任人收到通知 → 提交应对方案 → 方案执行 → 缓冲恢复 → 状态更新为"已化解" |
| 审批闭环 | 审批请求 → 正确路由到审批人 → 审批结果记录 → 例外放行记录理由 |
| 例外闭环 | 例外放行 → 记录到 exception_log → 季度回溯 → 异常部门审计 → 审计报告 → 整改完成 |
| 到账闭环 | 标记到账 → 验证通过/失败 → 通过则计入缓冲 → 失败则重新提交 → 连续2次失败触发审计 |
| 压力测试闭环 | 跑全量场景 → 生成报告 → 推管理层 → 红灯触发紧急任务 → 会议决议执行 → 下次测试验证改善 |
| Agent 动作闭环 | Agent 执行动作 → 责任人响应 → 任务状态更新 → 到期未响应自动升级 → 最终验证完成 |
| 参数修正闭环 | 统计准确率 → 判定修正方向 → 执行修正 → 记录修正日志 → 用户可见可覆盖 |

### 18.3 一句话总结

> **每一个模块都回答了三个问题：谁在什么条件下做什么？做了之后谁来验证？验证不通过怎么办？**
>
> 这就是"执行细节与闭环验证"——把"谁在什么条件下做什么、做了怎么验证"这三点全部写清楚，让系统从"演示方案"变成"能落地的系统"。
