# 责任机制设计 v11（风险分级 → 责任人 → 核实 → 钉钉确认 → 催办升级）

> 落地于现有工作台。不改动已冻结的 v1.2 现金流内核与 v8 三层风控判定；
> 责任机制只消费它们的**产出**（灯色 / 三态 / 清洗结果），自身不计算金额、不重判风险。

---

## 一、数据模型（5 张表）

建表语句唯一权威定义：`sql/v8_accountability_schema.sql`（DDL 同步登记在 `v8/db.py`）。

| 表 | 作用 | 关键字段 |
|---|---|---|
| `mfg_v8_owner_matrix_v1` | **风险分级 × 责任人映射** | level_code(HIGH/MID/LOW)、primary_owner、deputy_owner、escalate_to、review_sla_hours、confirm_sla_hours、urge_interval_hours、max_urge_times、enabled |
| `mfg_v8_matter_v1` | **事项主表（责任台账核心）** | matter_id、risk_level、lamp、state、round、current_owner、owner_role、assign_reason、due_at、confirm_due_at、urge_count、confirmed_at、confirm_result |
| `mfg_v8_review_v1` | **核实记录**（每轮一条） | review_id、matter_id、round、reviewer、reviewer_role、review_at、opinion、conclusion、next_action、evidence_json |
| `mfg_v8_confirm_v1` | **钉钉确认书** | confirm_id、matter_id、round、channel、recipients_json、message_id、status(pending/confirmed/rejected/expired)、confirm_url、token、confirmed_by、confirmed_at、comment、payload_json |
| `mfg_v8_urge_v1` | **催办记录** | urge_id、matter_id、confirm_id、seq、recipients_json、sent_at、trigger_reason、status |

留痕复用既有 `mfg_v8_audit_log_v1`：每次状态变更记录 `field_name=state, before/after`；
责任改派记录 `field_name=current_owner, before/after`；核实结论记 `field_name=conclusion`。

## 二、状态流转设计

```
SUBMITTED ──assign──> ASSIGNED ──begin──> IN_REVIEW ──complete──> PENDING_CONFIRM
                          ▲                                          │   │
                          │                              confirm ────┘   └── urge(超时)
                          │                                 ↓                   ↓
                          └──── reject（round+1 改派替补）◄── REJECTED         URGING
                                                            CONFIRMED(终态)      │
                                                                    └─超次数─> ESCALATED（转上级）
```

| 状态 | 含义 | 允许迁出 |
|---|---|---|
| SUBMITTED | 已提交未分派 | ASSIGNED、CLOSED |
| ASSIGNED | 已分派待核实 | IN_REVIEW、CLOSED |
| IN_REVIEW | 核实中 | PENDING_CONFIRM、ASSIGNED、CLOSED |
| PENDING_CONFIRM | 已核实，等待钉钉确认 | CONFIRMED、REJECTED、URGING、CLOSED |
| URGING | 超时催办中 | CONFIRMED、REJECTED、URGING、ESCALATED、CLOSED |
| ESCALATED | 催办超限已升级上级 | CONFIRMED、REJECTED、CLOSED |
| CONFIRMED | 已确认（终态） | — |
| REJECTED | 已驳回（过渡态） | ASSIGNED |
| CLOSED | 已关闭（终态） | — |

**流转规则（硬性）**
1. 迁移必须命中 `TRANSITIONS` 白名单，非法流转直接拒绝并回传 `allowed` 列表；
2. 驳回不做覆盖：round+1，优先改派替补人（已是替补则升级对象），历史核实记录全部保留；
3. 超时判定以 `confirm_due_at` 为准；催办一次则该时限顺延 `urge_interval_hours`；
4. 催办次数达 `max_urge_times` 后不再催办，直接升级至 `escalate_to` 并重置计数、发升级通知；
5. 每次状态变更 / 责任转移均写留痕（谁、何时、从什么改成什么）。

## 三、关键接口实现

### 3.1 MCP 工具层（`v8_mcp_server.py`，新增 9 个工具，工具总数 21）

| 工具 | 用途 | 关键入参 | 关键出参 |
|---|---|---|---|
| `acc.submit` | 提交事项并自动分派 | title, lamp/risk_level, industry, amount, source_ref | matter_id, assigned_to{owner,due_at}, state |
| `acc.review` | 核实（begin/complete 两步） | matter_id, step, reviewer, opinion, conclusion | review{reviewer,review_at,conclusion}, confirm{confirm_id,confirm_url,mode} |
| `acc.confirm` | 在线确认/驳回 | confirm_id, action, actor, comment, token | ok, state, round, reassigned_to |
| `acc.urge` | 人工催办 | matter_id, actor | urge_count, owner, dingtalk{mode,sent} |
| `acc.sweep` | 超时扫描（催办/升级） | as_of | urged[], escalated[], dingtalk_mode |
| `acc.ledger` | 台账查询 | state, risk_level, owner, keyword | items[]（含 overdue / overdue_hours） |
| `acc.history` | 责任链追溯 | matter_id | matter, reviews[], confirms[], urges[], flow[] |
| `acc.owners` | 映射查询/维护 | do=list\|upsert, level, primary_owner… | matrix{} / changed_fields[] |
| `acc.dingtalk_status` | 通道模式 | — | mode(real\|dry-run), note |

### 3.2 HTTP 接口（`v8_acc_server.py`，端口 8020）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 责任台账工作台（页面） |
| GET | `/api/acc/health` | 健康检查（数据库 + 钉钉通道模式） |
| POST | `/api/acc/submit` | 提交并分派 |
| POST | `/api/acc/review` | 核实（step=begin\|complete） |
| POST | `/api/acc/confirm` | 在线确认/驳回（带 token 校验） |
| GET | `/api/acc/confirm/view` | 确认书内容（令牌校验后返回） |
| GET | `/dingtalk/confirm` | **钉钉确认入口页**（接收人点击后在线确认或驳回） |
| POST | `/api/acc/urge` / `/api/acc/sweep` | 人工催办 / 超时扫描 |
| GET | `/api/acc/ledger` / `/api/acc/history` / `/api/acc/owners` | 台账 / 追溯 / 映射 |
| POST | `/api/acc/owners` | 维护调整责任人 |

统一返回：`{ok, code, data, error:{code,message,detail}, meta}`

### 3.3 钉钉通道（`v8/dingtalk.py`）

- 确认书正文含：**风险等级、事项描述、核实结论、确认入口**，接收人 = 核实人 + 替补人 + 升级对象；
- 确认入口为一次性签名链接：`/dingtalk/confirm?confirm_id=…&token=HMAC(secret, confirm_id)`，
  令牌不符直接拒绝，防篡改；
- 接收人点击「确认」或「驳回」→ 状态**实时回写** `mfg_v8_confirm_v1.status` 与事项主表；
- 超时未确认 → 自动发催办（seq 递增留痕）→ 超限自动升级；
- **真实 / 兜底双模式**：配置了 `DINGTALK_WEBHOOK` 或 `APP_KEY/SECRET` 才真发；
  未配置时为 `dry-run`，只落库并返回 `message_id=dryrun-…`，**绝不伪造送达**。

## 四、部署与验证

**1）建表**（管理员账号执行一次）
```bash
mysql -u root -p < sql/v8_accountability_schema.sql
# 授权（应用账号仅需 SELECT/INSERT/UPDATE）
```
**2）配置**（`deploy/.env`）：`CF_DB_*`、`CF_CONFIRM_BASE`（**必须是外网可达地址**，否则钉钉里点开无效）、
`CF_CONFIRM_SECRET`（必须替换）、`DINGTALK_WEBHOOK` 或 `DINGTALK_APP_KEY/SECRET`（留空则为 dry-run）。

**3）启动**
```bash
python mcp-server/program_v1/src/v8_acc_server.py     # 8020 责任机制服务与确认页
python mcp-server/program_v1/src/v8_mcp_server.py --http --port 8090   # MCP（stdio 时省略参数）
```

**4）验证**
```bash
python qwen-integration/verify_accountability.py   # 引擎层 29 项（含驳回重流转/催办/升级）
python qwen-integration/verify_acc_http.py         # HTTP 接口 26 项（含确认页令牌校验）
python qwen-integration/verify_v10.py --gateway    # 回归：v10 架构 28 项
```
当前实测：**29/29、26/26 全通过**；MCP 工具层 21 个可用，责任机制 9 个全部调通。
