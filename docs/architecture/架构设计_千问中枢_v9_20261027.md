# 架构设计 v9：千问办公为中枢，前端与 IM 为入口，服务器承载计算与数据

> 本文档只解决一件事：把 v8 的架构意图落成**可施工的边界、调用链与验证清单**。

---

## 0. 一句话定义

**千问办公是中枢与中转站。** 它不存数据、不算金额；它负责听懂人要什么（Agent 调度）、按什么顺序做（Skill 工作流）、以及伸手去调用谁（MCP）。
**所有算力、数据、密钥都在我们自己的服务器上。**

---

## 1. 分层与边界

| 层 | 组成 | 归属 | 职责 |
|---|---|---|---|
| 入口层 | 前端网页（独立站点）、钉钉、企业微信 | 外部 | 让人能触达系统；**不参与任何计算** |
| 中枢层 | Agent 调度、Skill 工作流、MCP 客户端 | 千问办公 | 理解意图、编排步骤、发起工具调用 |
| 执行层 | 计算引擎、MySQL MCP、Agent、MySQL | 我们服务器 | 算钱、留痕、回查、推理 |

**唯一允许产出金额的组件是计算引擎。** Agent 与 Skill 可以检索、整理、解释、路由，**但不得改写任何一个数字**。

---

## 2. 一次完整请求怎么走（这是全架构的核心链路）

```text
用户在前端点「计算」
   ↓ HTTPS
千问办公：Agent 理解意图 → Skill 决定步骤 → MCP 客户端发出调用
   ↓ JSON-RPC / MCP
计算引擎（Python，Decimal 整数分运算）
   ↓ 返回完整 result（金额 + 来源快照 + 算法哈希）
千问原样透传，不加工
   ↓
前端渲染 / 或经 Skill 触发钉钉、企微推送
```

用户要求保存时：
```text
用户明确指令 → Skill 校验 can_save_source_result
   → 计算引擎「按来源重算一遍」并与本次返回值逐项比对
   → 一致才写 MySQL（request_id 幂等）
   → 返回 record_id + payload_sha256，供精确回查
```

**「保前重算」不可省略。** 它保证落库的数字与用户看到的是同一遍计算，而不是模型转述过的内容。

## 4. 三个命门（未验证，任何一条不成立架构就要改）

### 命门一：千问办公的 MCP 客户端支不支持远程 HTTP？

- 已知：桌面端 **stdio 已验证可用**（连接器配置指向本机 `entry.py stdio`）。
- 未知：你的服务器在远端。若千问只能拉起**本机** stdio 进程，则"计算/MySQL 在远端服务器"必须靠一个本机 stdio 转发进程桥接。
- 协议文档 `千问办公_MySQL_MCP对接协议.md` §3.1 自己写明："千问是否支持自定义 MCP、传输方式、认证方式、定时执行与结果写回，**均需现场验证**。"
- **验证方法**：在千问连接器里把地址从 stdio 换成 `https://<域名>/mcp`（Streamable HTTP），看能否 `initialize` + `tools/list` 成功。

### 命门二：前端网页到底怎么连到千问？

- 你说"前端和千问有一个连接"。这需要千问办公有**对外 HTTP API** 供第三方网页调用。
- 若没有：前端只能直连我们自己的服务器，千问只存在于"对话侧"。**那图上「前端 → 千问」这条线画不上**，架构要改成双入口而非串联。
- **验证方法**：让千问列出它对外暴露的 API / SDK / webhook 能力，并给出一次真实调用示例。不接受的证据形式："聊天里能调用所以网页也能"（`千问Pages_前端发布接续任务_20261027.md` 里已经明确否定过这种推理）。

### 命门三：钉钉 / 企业微信是入口还是出口？

- v8 里钉钉是**出口**（推送预警、日报、审批通知）。
- 若你要的是**入口**（用户在钉钉里下令"跑一下现金流"），方向相反，要求千问能接收 IM 回调——这是完全不同的能力。
- **必须明确**：只做推送、只做接收、还是双向。

## 5. 安全红线（MCP 一旦接上数据库，这些是不可让步的）

协议文档 §3.3 已写正确做法，此处列为施工期硬约束：

1. **绝不暴露"执行任意 SQL"的工具。** 只暴露参数化的白名单工具（`log_to_mysql` 这类），禁止 `raw_sql` / `execute_query`。
2. **企业 ID、操作者 ID、角色从已认证主体解析**，不信任模型传入的同名字段——模型可以被提示词注入诱导传假的企业 ID。
3. **所有 SQL 带服务端解析的企业条件**，不靠调用方自觉。
4. **MySQL 不对公网暴露**，只绑 `127.0.0.1`；MCP Server 走 Nginx 反代 + HTTPS。
5. **金额字段的写入只能是计算引擎本次返回的完整 result**，不允许模型拼装、补零、四舍五入或跨来源拼接。
6. **密钥在服务器侧**，不进前端、不进 Skill 文本、不进仓库。
7. 校验 `Origin`；本地服务只监听回环地址。

## 7. 对外口径（能说什么，不能说什么）

**可以说的：**
- 千问办公是中枢：意图理解、工作流编排、工具调用都由它完成。
- 计算由确定性程序完成，AI 不参与金额运算。
- 数据留在企业自有服务器。

**还不能说的（缺证据）：**
- ❌ "调用了千问的 Skill 做计算" —— 实际是千问调用**我们的** MCP。
- ❌ "已打通远程 MCP" —— 命门一未验证。
- ❌ "前端已接入千问" —— 命门二未验证。
- ❌ "支持钉钉/企微指令下发" —— 命门三未验证，目前只有推送设计。

## 8. 与今天下午结论的关系

- 探针结论（N1 不能注入 env、N3 30 秒超时、N5 删网页清库）**对本架构大部分失效**，因为计算与存储都在我们服务器、前端是独立站点。这三条只约束"若前端托管在千问 Pages"这一条路。
- N2（第三方依赖可打包）对纯 Python 后端无影响。
- **答辩 Q1（"搬去别家也能跑，凭什么叫以千问为核心"）在本架构下可以翻案**：删掉千问，整个编排链路断掉，前端无数据。这是耦合，不是托管。前提是命门一、二成立。
