# 前端接入 MCP：方案对比与行动清单

> 版本：v1 · 2026-10-28
> 前置文档：`docs/MCP服务设计_千问办公作为后端_v1.md`
> 目标：让"千问办公为后端中枢、MCP 统一调算法"这句话在代码里成立，而不只是写在方案里。

---

## 一、五个候选方案

### 方案 0：维持现状（双通道）—— 基准项

**链路**：前端 → `/api/*` → 直连引擎；千问 → `/mcp` → MCP 工具 → 引擎。

- **好处**：零工作量；功能全通；两条路结果恒等（共用 `service.py`）。
- **坏处**：**架构与方案文档自相矛盾**。文档写"MCP 是唯一能力出口"，代码里前端绕过 MCP；评委会问"你的 MCP 到底起什么作用"，答案只能是"只给千问用"。
- **隐性成本**：每加一个能力要改两处（HTTP 路由 + MCP 工具），迟早出现两边行为不一致。
- **要做什么**：无。
- **结论**：可以撑过内部演示，撑不过答辩追问。

---

### 方案 ①：前端直连 MCP（浏览器 → `/mcp`）

**链路**：前端 JS 直接 POST `/mcp`，自己组 JSON-RPC、管 session、解析 SSE。

- **好处**：改动集中在页面；后端不用动；链路上确实"经过 MCP"了。
- **坏处（致命）**：**千问被彻底边缘化**。前端直连引擎，千问在架构里只剩一个"也能调"的旁观者，与"千问办公为后端中枢"直接冲突，答辩致命。
- **其他坏处**：session/SSE 逻辑要在浏览器里重写一遍；MCP 端点必须对公网开放且无鉴权（当前无 token），等于把 `save_cashflow_result` 这种写库工具暴露给任何人；CORS 与 Host 白名单还要再放行。
- **要做什么**：页面加 MCP 客户端（约 150 行 JS）；给 `/mcp` 补鉴权；处理 CORS；7 个接口逐个改。
- **结论**：**明确不推荐**。技术可行，方向错误。

---

### 方案 ②：后端做 MCP 客户端（路径乙 · 最小改动）

**链路**：前端 → `/api/*` → `public_server.py`（MCP 客户端）→ `:8123` → 引擎。

- **好处**：
  - 前端页面**零改动**，用户无感；
  - 砍掉 `import program_workbench` 直连，MCP 成为唯一计算与落库出口，消除双通道；
  - 工作量最小，可快速验证，出问题容易回滚；
  - 鉴权只需加在后端到 8123 的回环调用上，不扩大公网暴露面。
- **坏处**：
  - **千问仍然不在前端链路上**，只是"能力出口统一了"，"千问为中枢"依旧只在千问自己的会话里成立；
  - 多一跳进程间调用，要处理 session 失效、超时、返回结构解包；
  - 8123 挂掉前端就不可用（可用性耦合）。
- **要做什么**：
  1. 新增 `mcp_client.py`（session 管理 + SSE 解析 + 重连）；
  2. `public_server.py` 的 7 个路由改为调 MCP，删除引擎直连 import；
  3. 解包 `structuredContent` / `content[0].text`；
  4. MCP 不可用返回 `503 mcp_unavailable`，**禁止降级为本地直连**；
  5. 跑金值回归（177000.00 / 140000.00 / −1000.00）+ 停 MCP 必须失败的反向验证。
- **结论**：**止血首选**。先让架构不自相矛盾，再谈千问中枢。

---

### 方案 ③：启用 B 作为统一入口（路径甲 · 推荐目标态）

**链路**：前端 / 千问 → **B `frontend.dispatch`**（:8090）→ A（:8123）→ 引擎。

- **好处**：
  - **门面与引擎分层**：前端和千问面对同一套 action 语义，新增能力只改 B 的路由表；
  - B 的协议层是现成的：零依赖、双传输、统一错误封装、action 注册机制、自测脚本；
  - **鉴权方案现成**（`CF_MCP_TOKEN`，未配置拒绝启动），顺手补上 A 目前无 token 的高风险洞；
  - 千问侧只需注册一个 B，就能用到全部能力，Skill 编排更干净。
- **坏处**：
  - **三跳链路**（前端→B→A→引擎），排错层次变多；
  - 多一个服务要部署、监控、保活；
  - B 的 `biz_*` 目前是示例，**不接真业务就上线等于造假**；
  - 若 B 只做转发，会被质疑"多这一层图什么"。
- **要做什么**：
  1. 把 `biz_risk_assess` / `biz_ledger_query` 的示例实现换成对 A 的真实调用；
  2. 在 `ACTION_ROUTER` 注册 `cashflow.calculate/save/query`、`source.list/audit` 等 action；
  3. `ACTION_SCHEMAS` 补入参校验，`source_id` 限定四个合法来源；
  4. 写 `cf-mcp-frontend.service`，配 `CF_MCP_TOKEN`，部署到服务器；
  5. Nginx 加 `/mcp-frontend` 反代；
  6. 千问侧注册 B（用现成 config 的 `_http_alternative` 段）；
  7. 前端切到 B（过渡期可由 `public_server.py` 代做协议转换，页面零改动）。
- **结论**：**目标架构**。适合作为最终形态，但建议排在方案②之后，不要一步到位。

---

### 方案 ④：前端经千问对话接口（最贴合"千问为中枢"）

**链路**：前端 → 千问对话入口 → 千问意图解析 + Skill 编排 → MCP → 引擎 → 回千问解释 → 前端。

- **好处**：架构叙事最完整，千问名符其实是中枢；演示效果最好，"每一次业务动作都由千问发起"这句话完全成立；合规论证（v8.2 §1.4）最省力。
- **坏处**：
  - **依赖千问是否开面向自研前端的调用入口**，这点目前未验证，是硬前提；
  - **把大模型不确定性引进金额链路**：同样的请求可能走出不同工具序列，金融计算不该这样；
  - 延迟从 0.03 s 变成秒级甚至十几秒；千问侧限流/故障直接拖垮前端；
  - 结果格式需要额外约束，否则前端拿不到稳定结构。
- **要做什么**：先验证千问开放接口能力；定义结构化输出契约；做幂等与超时兜底；关键写操作加人工确认。
- **结论**：**只适合做演示路径，不适合做金额主链路**。可作为③之上的增强，而非替代。

---

### 方案 ⑤：合并成单一 MCP 服务（B 的 action 并入 A）

**链路**：前端 / 千问 → **一个 MCP 服务**（A 的 9 个工具 + B 的 dispatch 门面）→ 引擎。

- **好处**：少一个服务、少一跳；部署与运维最简单；鉴权只配一处；仍然消灭双通道。
- **坏处**：要改 A 的代码（把 B 的门面逻辑移植进 `build_mcp()`），动的是线上正在跑的服务；B 现有的独立自测要重写；失去"门面可独立演进"的弹性。
- **要做什么**：把 `ACTION_ROUTER` / `ACTION_SCHEMAS` 移植进 A；注册 `frontend.dispatch` 工具；`public_server.py` 改调它；补 token；回归金值。
- **结论**：**③的简化版，长期来看可能是最划算的形态**。若不想多养一个服务，选它不选③。

## 三、推荐路线：分三步，不要一步到位

**第一步：方案②止血** —— 先消灭双通道，让"MCP 是唯一能力出口"在代码里成立。前端无感、可回滚、风险最低。

**第二步：在③和⑤之间做一次决策** —— 愿意多养一个服务选③（门面独立演进），想运维最省选⑤（合并单服务）。两者架构叙事等价，**不必都做**。

**第三步：方案④作为演示增强** —— 先花最小成本验证"千问能否被自研前端调用"。验证不过就只在千问侧演示 workflow，不影响主链路。

**明确排除方案①**（方向错误，把千问边缘化）；**方案⓪仅限内部临时演示**，不能作为交付状态。

---

## 四、无论选哪条都要做的四件事

1. **补鉴权**：`/mcp` 当前公网无 token，直接复用 B 的 `CF_MCP_TOKEN`（未配置拒绝启动）。这是独立高风险项，不该等架构整改。
2. **金值回归**：任何改动后必须重跑三组基准——`177000.00` / `140000.00` / `-1000.00 且 can_save=False`，以及原埋错样例仍然 `error blocked`。
3. **禁止静默降级**：MCP 不可用时返回明确错误，**不允许悄悄退回本地直连计算**，否则双通道会以"容错"的名义复活。
4. **同步文档**：改完更新 `v8_完整方案.md` §1.7 与 §3.2 的"当前实际链路"，把"存在偏差"改为实际状态，避免文档再次与代码脱节。

---

## 五、一句话结论

**先用②把架构矛盾消掉（小改动、页面零变化），再在③/⑤里挑一个做最终形态，④只当演示增强，①不要做。**
