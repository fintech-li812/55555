## 1. 连接信息清单（全部来自代码，非猜测）

### 1.1 两侧地址与端口

| 角色 | 文件 | 本机端口 | 生产端口 | 生产入口 |
|---|---|---|---|---|
| 主站（页面 + 主 API） | `mcp-server/program_v1/src/public_server.py` | 8000（`WORKBENCH_PORT`） | 8000 | Nginx `/` → 8000 |
| V8（三层风控） | `mcp-server/program_v1/src/v8_server.py` | 8010（`CF_V8_PORT`） | 8010 | Nginx `/v8/` → 8010 |
| 责任机制（未接入本页） | `v8_acc_server.py` | 8020 | 8020 | 未对外暴露 |

生产链路：`https://workbench.example.com/unified` → Nginx → `/` 命中 8000（public_server）；
页面里 V8 的 `/v8/api/v8/*` → Nginx `/v8/` → 8010（v8_server）。
**本机没有 Nginx，这是原来联不通的根因**：V8 请求会打到 8000，而 8000 没有这些路由，只能 404。

### 1.3 鉴权凭据的传递方式

1. 服务启动时生成令牌：`WORKBENCH_TOKEN`，未设置则随机生成并打印一次。
2. 服务在返回页面时把 HTML 里的 `__CSRF_TOKEN__` 占位符替换成真实令牌
   （这就是 `/`、`/console`、`/unified` 必须由本进程提供、不能用 Nginx 静态文件托管的原因）。
3. 页面从 `<meta name="workbench-token">` 读取，写接口在
   `X-Workbench-Token` 头里带回。
4. 服务端对 **POST** 做 `secrets.compare_digest` 校验；
   GET 不校验。另外还有 Host 白名单 + Origin 校验，不匹配返回 403。

### 1.4 技术栈与既有启动方式

- 后端：Python 标准库 `http.server`（无框架、无构建），MySQL 用 PyMySQL。
- 前端：单文件原生 JS（`web/统一工作台.html`），唯一全局 `W`，模块间通过 `W.store` 通信，
  请求统一走 `W.api`（`base.main` 主站 / `base.v8` V8）。
- 既有启动方式：生产 `deploy/serve.py`（先加载 `deploy/.env` 再调用 public_server）；
  本机原先只有 `打开工作台.cmd` → `启动工作台.ps1`（只起 18766 的老页面，不含 V8 与统一页）。

## 2. 改动清单（共 3 处代码 + 2 个脚本）

### 2.1 `public_server.py`：新增 V8 同源反向代理（核心改动）

新增内容：

- `V8_ORIGIN`：默认 `http://127.0.0.1:<CF_V8_PORT 或 8010>`，可用 `WORKBENCH_V8_ORIGIN` 覆盖。
- `V8_ENABLED`：上游主机名必须是 `127.0.0.1 / localhost / ::1`，避免被当成任意内网代理。
- `_is_v8(path)` / `_v8_upstream(path)`：`/v8/api/v8/x` 与 `/api/v8/x` 都转发到上游的 `/api/v8/x`。
- `Handler.proxy_v8(method, body)`：原样转发请求，原样带回响应。
  - 上游 4xx/5xx **照样透传**（页面因此能看到真实错误，而不是被包装成「成功」）；
  - 上游连不上 → 502 `v8_unavailable`，绝不用快照冒充。
- 路由：GET 分支最前面判 V8；POST 分支放在**令牌校验之后**，
  因此 V8 的写请求在本机也受会话令牌保护，上游拿到的仍是页面带来的原始令牌与请求体。
- `main()` 改用 `ThreadingHTTPServer`：一次 V8 评估约 0.5 秒，不能把整个页面堵住。

**为什么用代理，而不是让前端直连 8010？**
页面由 8000 下发且带 CSP `connect-src 'self'`，浏览器会直接拦掉跨域 fetch。
走同源代理后：后端**完全不需要开 CORS**，CSP 也不用放宽，前端一行不改。

对生产无影响：Nginx 的 `location /v8/` 比 `location /` 更具体，请求仍直接到 8010，
这段代理在生产不会被触发；即便触发，行为也与直连一致。

同时在本机的后端控制台里补上了 V8 服务与 5 个 V8 端点（可点「测」直接探测），
让控制台如实反映统一页的真实流量。

### 2.2 `v8_server.py`：修复 `_ensure` 无限递归

原实现：

```python
def _ensure(cur):
    try:
        _ensure(cur)          # 递归调用自己
    except Exception:
        pass
```

它撞到 `RecursionError` 后被同一个 `except` 吞掉，DDL **从未真正执行过**，
等于永远建不了 `mfg_v8_risk_log_v1`。改为：

```python
    try:
        cur.execute(DDL)
    except Exception:
        pass
```

容错语义不变：`cf_app` 无 CREATE 权限或表已存在时照旧被忽略，
只有「表确实缺失且账号有权限」这条路径从不可能变成可能。

### 2.3 `启动一体化工作台.ps1` + `打开一体化工作台.cmd`（新增）

一条命令拉起 V8 → 主站，再可选择拉起隔离 MySQL。

- 参数：`-MainPort 8000`、`-V8Port 8010`、`-DbPort 3307`、`-WithDatabase`、`-OpenBrowser`。
- 从 `deploy/.env` 读数据库配置，**只注入子进程**，不写用户环境、不打印口令。
- 自动推导 `WORKBENCH_ALLOWED_HOSTS`（必须与浏览器地址栏一致，否则 403）。
- 端口已在监听时复用现有进程，不重复启动；启动后等端口真正可连再返回。

踩到并绕开的两个坑（都写进注释了）：

1. PS 5.1 的 `Start-Process` 与 .NET 的 `ProcessStartInfo.EnvironmentVariables`
   都会把当前进程环境整个快照一遍，环境里同时存在 `HTTPS_PROXY` 与 `https_proxy`
   时直接抛「已添加项…字典中的关键字」。改用 `cmd` 的 `set` 注入。
2. `set K=V && ...` 会把 `&&` 前的空格算进值里（`WORKBENCH_HOST` 变成 `127.0.0.1 `，
   Python 拿去查 DNS → `getaddrinfo failed`）。必须写成 `set "K=V"`。

## 4. 常见问题的应对方式

### 4.1 跨域（CORS）

**首选做法是消灭跨域，而不是处理它**：页面只从 8000 这一个源取数，
V8 由主站内部代理。因此：

- 后端无需 `Access-Control-Allow-Origin`；
- 页面 CSP `connect-src 'self'` 保持不动，安全性不下降；
- 浏览器不会发预检（OPTIONS），也没有 cookie/凭据跨域问题。

若将来确实要让页面指向另一个源（在页面「后端连接设置」里填外源地址），
则必须同时满足三件事，缺一不可：

1. 目标服务返回 `Access-Control-Allow-Origin: <页面所在源>`，
   并对 POST 允许 `Content-Type` 与 `X-Workbench-Token` 头；
2. 下发页面的服务放宽 CSP 的 `connect-src`，把该源加进去；
3. 令牌问题：静态打开的页面拿不到服务端替换的令牌，
   写接口必然 403。所以这条路只能用于只读展示。

**结论：始终通过服务端下发的 URL 打开页面（`/unified`），不要把 HTML 当静态文件双击打开。**

### 4.2 环境变量

| 变量 | 作用 | 默认 |
|---|---|---|
| `WORKBENCH_HOST` | 监听地址 | `127.0.0.1` |
| `WORKBENCH_PORT` | 主站端口 | 18767（生产由 `.env` 指定 8000） |
| `WORKBENCH_ALLOWED_HOSTS` | Host/Origin 白名单 | `127.0.0.1:<PORT>,localhost:<PORT>` |
| `WORKBENCH_TOKEN` | 会话令牌 | 空则随机生成并打印一次 |
| `WORKBENCH_V8_ORIGIN` | 代理上游 | `http://127.0.0.1:<CF_V8_PORT 或 8010>` |
| `WORKBENCH_V8_TIMEOUT` | 代理超时（秒） | 120 |
| `CF_V8_PORT` | V8 监听端口 | 8010 |
| `CF_DB_*` | 数据库 | 来自 `deploy/.env` |

注意：`WORKBENCH_ALLOWED_HOSTS` 必须与浏览器地址栏完全一致，
用 `localhost` 访问就不能只配 `127.0.0.1`，否则 403 `host_not_allowed`。
启动脚本已按端口自动推导，改端口时不必手动维护。

### 4.3 接口路径不一致

统一页对 V8 用 `/v8` 前缀 + `/api/v8/*`，即 `/v8/api/v8/*`；
旧的 `v8_工作台.html` 用相对路径 `api/v8/*`（因为它由 8010 自己在 `/` 上提供）。
代理同时接受 `/v8/api/v8/*` 与 `/api/v8/*`，两种写法在本机都能通。

### 4.4 端口不一致 / 端口被占用

- 启动脚本会在启动前检查端口，已被占用则复用现有进程并提示 pid，不会重复起。
- 换端口用 `-MainPort` / `-V8Port`，`WORKBENCH_ALLOWED_HOSTS` 会跟着自动改。
- 注意 8000 与生产一致，若本机 8000 被别的程序占了，换 18000 之类即可，
  不要去改 `deploy/.env`（那是生产配置）。

### 4.5 本机隔离库起不来：undo 表空间的死循环（已修）

现象：

```text
[ERROR] [MY-013039] [InnoDB] Can't create UNDO tablespace innodb_undo_001
         since '…\undo_001' already exists.
```

**真正的成因有两层**，只修第一层不够：

1. `deploy/mysqld-standalone.cnf` 里 `innodb-undo-directory` 原本指向 datadir 本身，
   InnoDB 启动时想重建，却撞上同名文件。→ 改为指向独立目录 `deploy/.mysqlundo/`。
2. 更要命的是**死循环**：若 mysqld 上次是被强杀的，崩溃恢复会把「创建 undo 表空间」
   这条**数据字典记录回滚掉**，于是下次启动又要重建，却撞上上次创建残留的文件，
   再次失败。表现为「成功一次，之后每次都起不来」。

对策（已写进 `启动一体化工作台.ps1` 的 `Start-StandaloneMySql`）：
每次启动前先把 undo 目录里的文件归档到 `deploy/.undo-backup/last/`，
让 InnoDB 干净重建。只动 undo 表空间，**不碰 datadir，表数据不受影响**
（修复后回查到的 8 条留痕含修复前写入的记录，即数据完好）。

若手工操作，顺序是：

```powershell
# 1) 备份（原始 undo 另存，可完整还原）
Copy-Item deploy\.mysqldata\undo_002 deploy\.undo-backup-20261028\
# 2) 把 undo 文件移出 datadir（用 Move 而非 Remove，可回溯）
Move-Item deploy\.mysqldata\undo_002 deploy\.mysqlundo\
# 3) 改配置
#    innodb-undo-directory=D:/CashflowRiskWorkbench/deploy/.mysqlundo
# 4) 起服务；此后由启动脚本自动处理归档
& 'D:\CashflowRiskWorkbench\启动一体化工作台.ps1' -WithDatabase
```

### 6.4 真实根因：令牌哨兵被无差别替换（已修）

此前把「— / V8」「数据库 未连接」归结为抓取工具的时序假象，**这个判断是错的**。
真实原因是服务端注入令牌时，把页面 JS 里的哨兵字符串也一起替换了。

`web/统一工作台.html` 中 `__CSRF_TOKEN__` 共出现 **2 次**：

| 位置 | 作用 | 是否应被替换 |
|---|---|---|
| 第 6 行 `<meta name="workbench-token" content="__CSRF_TOKEN__">` | 承载真令牌 | 是 |
| 第 621 行 `var served = token !== '__CSRF_TOKEN__';` | JS 判断「页面是否由本服务提供」的哨兵 | **否** |

而 `public_server.py` 用的是 `.replace("__CSRF_TOKEN__", TOKEN)`，Python 的
`str.replace` 会替换**全部**出现。替换后 JS 变成 `token !== '2659b808…'`，
而 `token` 本身就是 `2659b808…` → **`served` 恒为 `false`**。

`W.api.call()` 的短路逻辑为 `if(!served && !root) throw`：

- 主站请求（`root = ''`）→ **在发出之前**就被拦掉，请求根本不出浏览器；
- V8 请求（`root = '/v8'` 非空）→ 不受该判断约束，正常发出。

外部症状：Nginx 访问日志里 `/api/status`、`/api/console`、`/api/sources`
的记录数为 **0**，而 `/v8/api/v8/*` 全部正常。这与「接口慢导致超时」有本质区别 ——
慢至少会留下访问记录，而这里是根本没有记录。

**判断依据（三层递进）：**

1. 服务端并发 4 个请求全部 200、0.11 秒 → 排除服务端慢或挂起；
2. 核对访问日志：客户端 IP 在多次会话中只有 `/v8/` 请求，三个主站 API 全部为 0
   → 请求没有到达服务端；
3. 差异只体现在 `root` 是否为空 → 反查 `call()` 的短路条件 → `served` 为假
   → 源头是无差别替换波及了哨兵。

### 6.5 修复内容

| 文件 | 改动 |
|---|---|
| `public_server.py` | 新增 `_page()`，三处替换改为只替 **meta 标签内**的 `content="__CSRF_TOKEN__"`，不再裸露替换整个字符串 |
| `统一工作台.html` | 启动时补 `W.modCN.init()`：控制台数据同时供总览使用，原先只在切标签时才加载，总览只能拿到探测带回的两个字段 |
| `统一工作台.html` | `probe()` 改为 `Promise.all` 并行，避免徽标明显滞后于已拿到数据的总览卡片 |
