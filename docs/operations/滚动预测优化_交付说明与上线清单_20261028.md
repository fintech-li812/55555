## 一、关键改动

### 1. 采样块长自动对齐业务周期（影响最大的一项）

**原状**：`block_length` 固定为 4（或用户填任意值），与数据的真实周期无关。

**问题**：移动块自助法（moving-block bootstrap）用长度为 L 的连续块拼接未来 13 周。
若 L 与真实周期不整除，块边界会**切断周期结构**，把原本会相互抵消的误差变成同向叠加。

**实测**（合成数据，含 7 周周期）：

| 块长 | 13 周累计误差标准差 | 与真实分布的 KS 距离 |
|---|---|---|
| 4（原默认） | 33.64 | 0.327 |
| **7（对齐周期）** | **11.26** | **0.068** |

真实历史窗口的标准差是 10.07。**块长 4 把风险敞口放大了 3.3 倍。**

**改动**：`detect_seasonality()` 用自相关峰值检测周期；`select_block_length()` 在检测到
周期时对齐，未检测到时回退到配置值——**并记录理由，不静默降级**。

```jsonc
"block_rationale": "aligned block_length 4 -> 7 (detected 7-week cycle)"
```

**校准验证**（名义 90% 预测区间的实际覆盖率）：

| 配置 | 标准差 | 覆盖率 | 标准差/真实值 |
|---|---|---|---|
| 块长固定 4 | 7.518 | 100.0%（区间过宽失效） | 1.55x |
| **自动对齐** | **4.958** | **91.5%** | **1.02x** |

业务含义：优化前会系统性高估缺口 55%，导致过度融资与误报警。

**必须说清的负面结果**：周期对齐对 **MAE 几乎没有改善**（−0.2% ~ +0.2%）。
这不是失败——块长影响的是**分布形态**（方差、尾部），不是**均值路径精度**。
用 MAE 评价它本身就是选错指标。收益体现在风险度量的校准上。

### 2. 偏差处理改为数据驱动的自动判断

**原状**：误差均值原样进入路径，13 周后积分成 `13 × μ` 的漂移。

**关键认知**：去偏**不是无条件正确**。分两种情形：

- 均值是预测流程的**持续性系统缺陷** → 下季度还在 → 去掉会把预测推向反方向
- 均值是**抽样噪声** → 真实偏差为 0 → 带上只是平添漂移

**验证**（两种数据机制下对比三种策略）：

| 数据机制 | 强制去偏 | 强制保留 | **自动** | 最优 |
|---|---|---|---|---|
| 持续性偏差 +1.5 | MAE 6.332 | **5.002** | **5.002** | 保留 |
| 无系统偏差 | **4.727** | 5.002 | **4.727** | 去偏 |

**自动策略在两种场景下都精确选中了最优（差距 0.00%）**，相对最差策略改善 5.5%~21%。

**改动**：`resolve_bias()` 对每列做 t 检验（α 默认 0.05）。显著 → 保留；不显著 → 去除。
逐列判断，决策与 p 值一并写入结果：

```jsonc
"bias": {"mode": "auto",
         "note": "receipts: mean -0.3153 not distinguishable from zero (p=0.5080), removed; ..."}
```

t 分布 p 值自己实现（不完全贝塔连分式），与 `scipy.stats.t` 对照最大误差 **1.7e-15**，
因此不引入 scipy 依赖。

### 3. 增量更新

`RollingState` 维护 sum / sumsq，追加一周是 **O(1)**，不重扫历史。

实测：94 次追加，增量 0.85 ms vs 全量重建 22.22 ms → **26.1x**。

**一处反直觉的设计**：自相关**故意不做增量累积**。滑动窗口模式下，保留的行与
运行中的交叉积会脱节，一个悄悄过期的统计量比一次廉价的重算更危险。改为从有界窗口
重算，成本摊销 O(1)。滑动窗口测试：窗口 52 行时自相关与窗口内直算完全一致。

### 4. walk-forward 样本外评测

`walk_forward_backtest()` 对每个预测原点，只用**该原点之前**的误差做预测，与之后的
实际值比对——不泄漏未来信息。各原点共用随机数流（common random numbers），
压低原点间比较的方差，可用更少抽样达到同等精度。

**数据模型上的一个坑**：周期检测不能用「按原点拼接的 13 周块」。我第一版这么做，
检测出来的「周期」恒等于块长 13。改为误差序列按**日历周**连续排列后，才正确检出 7 周周期。

## 二、多种实现路径的取舍

用户要求说明取舍，以下 6 处是关键决策点。

### 取舍 1：偏差处理 —— 强制去偏 / 强制保留 / 自动检验

| 方案 | 优点 | 缺点 |
|---|---|---|
| 强制去偏 | 简单，消除漂移 | 偏差是持续性时**反而变差**（MAE +21%） |
| 强制保留 | 简单 | 偏差是噪声时漂移累积 |
| **自动 t 检验** | 两种情形都选中最优 | 多一个 α 参数；小样本功效不足 |

选自动。理由：两种错误方向的代价都不小，而判断依据（p 值）可以写入结果供复核。

### 取舍 2：块长 —— 固定 / 自动对齐 / 不用块（i.i.d.）

| 方案 | 优点 | 缺点 |
|---|---|---|
| 固定 | 可预测、可复现 | 与周期冲突时风险敞口高估 55% |
| **自动对齐** | 分布校准误差从 1.55x 降到 1.02x | 引入检测阈值；弱信噪比时可能误判 |
| 不用块（block=1） | 最简单 | 完全破坏时间依赖，实测与固定 4 同样失真 |

选自动对齐，但**保留固定值作为回退**，并在结果里写明选了什么、为什么。

### 取舍 3：持久化 —— 存完整 payload / 只存摘要

| 方案 | 优点 | 缺点 |
|---|---|---|
| **存完整 payload (JSON)** | 一次查询拿到全部结果，可复现 | 单条约 4.6 KB；需容差校验 |
| 只存摘要 + content hash | 表小、写入快 | 查详情需回对象存储，多一跳 |

选存完整 payload。单条 4.6 KB、每周一次，一年不到 240 KB，换取查询简单性是划算的。

### 取舍 4：一致性校验 —— 位级相等 / 容差比较

**踩过坑**：MySQL 的 JSON 列把数字经 DOUBLE 重新序列化，
`0.9127583004940999` 读回变成 `0.9127583004941`。位级相等会让**每一次运行都被自己的
校验判失败**。改为结构比较 + 浮点容差（`rel=1e-12`），键的集合、类型、布尔与字符串仍要求精确。

### 取舍 5：建表时机 —— 运行时自动建 / 部署时管理账号建

| 方案 | 优点 | 缺点 |
|---|---|---|
| 运行时 `CREATE IF NOT EXISTS` | 部署省事 | 违反最小权限；每次运行都试一次 DDL |
| **部署时管理账号建一次** | 运行时账号只需 SELECT/INSERT | 多一个部署步骤 |

选后者。第一版做的是前者，在服务器上直接撞上 `cf_app` 无 CREATE 权限——
这个报错其实是正确的安全设计，**是代码错了，不是权限错了**。

### 取舍 6：重试范围 —— 全部重试 / 区分永久错误

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全部重试 | 实现简单 | 表缺失、权限不足会被重试 3 次，白等 6 秒还掩盖真实原因 |
| **区分永久错误** | 立即暴露真实问题 | 需要维护错误码分类 |

选区分。`permanent=True` 的错误（1142 权限、1146 表缺失）首次即抛出，消息里直接给出
修复指引。

**附带修掉的真 bug**：pymysql 的异常**没有 `errno` 属性**，编号在 `args[0]`。
第一版只读属性，导致重复键被当成可重试错误——幂等重跑从 325 ms 拖到 6.3 秒。

### 一条诚实的边界

设计工作」，不能证明「真实业务数据上收益有多大」。真实数据接入后必须重跑

- 周期检测在真实信噪比下是否仍显著
- `min_strength=0.30` 阈值是否需要按行业调整
- 偏差的 t 检验在短历史（26~52 周）下功效是否足够

## 四、回滚方案

### 回滚触发条件（任一即回滚）

- 新建表写入失败率 > 5%
- 单次运行 > 600 秒（当前 287 ms，余量三个数量级）
- 出现 `read-back mismatch`（一致性校验失败）
- 影响原有 5 个服务（端口冲突、内存、磁盘）

### 回滚步骤（约 2 分钟）

```bash
# 1. 停调度，不再产生新运行
systemctl disable --now cf-rollcast.timer
systemctl stop cf-rollcast.service

# 2. 备份后清空新表（用管理账号，cf_app 无 DELETE 权限）
mysqldump cfqa_workbench cf_rollcast_runs_v1 cf_rollcast_errors_v1 \
    > /root/rollback-rollcast-$(date +%Y%m%d).sql
export CF_DB_USER=cfadmin CF_DB_PASSWORD=$(cat /root/.cfadmin.pw)
mysql -e "DROP TABLE IF EXISTS cfqa_workbench.cf_rollcast_errors_v1;
          DROP TABLE IF EXISTS cfqa_workbench.cf_rollcast_runs_v1;"

# 3. 移除单元
rm -f /etc/systemd/system/cf-rollcast.{service,timer} /etc/logrotate.d/rollcast
systemctl daemon-reload

# 4. 确认原有服务完好
systemctl is-active cf-workbench cf-mcp-http cf-mcp-frontend nginx mysql
systemctl --failed
```

**原引擎 `risk_model.py` 全程未改动，因此不存在「回滚算法」这一步**——
现有工作台对本模块零依赖，停掉即完全恢复。

### 数据保留

回滚前已 `mysqldump` 备份。输出文件在 `/var/lib/rollcast/out/`（保留 120 天），
日志在 `/var/log/rollcast/`。

## 五、灰度发布

当前是**一次性全量上线**，因为：本模块与现有工作台零耦合（不接前端、不改原引擎、
只新增两张表），且频率为每周一次，出问题的影响面是「少一份预测报告」，不是「线上事故」。

| 阶段 | 动作 | 观察 |

| 1. 影子运行 | `--no-persist` 跑 2~4 周，结果只写文件 | 比对 `latest.json` 与人工测算 |
