# 算法开关说明

> 适用范围：V8 风控工作台（`mcp-server/program_v1`）
> 最后更新：2026-10-29

## 1. 为什么要有开关

算法侧的几项改动都带**业务口径**含义：同一份输入，在不同口径下会落到不同灯色。

| 改动 | 业务含义 |
|---|---|
| 默认算法 v8 / ra-next-0.1 / v1 | 三版的 Q 口径不同，灯色阈值是各自标定的 |
| 证据不足时是否放行绿灯 | 风控的保守程度：宁可多报黄，还是恢复三档判别 |
| Benford 适用性声明 | 第一层的数值能不能作为结论依据 |
| Q 是否参与融合判别 | 第一层在数据质量报告与决策依据之间的定位 |
| 池级模型缓存 | 纯性能（15× 提速），行为等价 |

把它们写死在代码里，等于把业务裁决固化成技术细节，事后既无法回退也无法灰度。
开关化的前提是：**每个默认值都等于加开关之前的行为**，所以不配置任何东西时，
系统表现与改造前逐位一致。

## 2. 四级取值

```
请求参数  >  环境变量  >  配置文件  >  内置默认
(灰度/A-B)   (运维/容器)  (随代码进仓)  (代码里的常量)
```

- **请求参数**：`GET /api/v8/assess?algo=v1&evidence=loose`、POST `/api/v8/save` 的 body、
  `engine.assess(...)` 的关键字参数。用于灰度与人工复核。
- **环境变量**：`CF_V8_*`。用于容器 / systemd 部署，不改文件、不发版。
- **配置文件**：`deploy/algorithm.config.json`（可用 `CF_V8_CONFIG` 改路径）。
  随代码进仓库，是版本化的基线口径。
- **内置默认**：`v8/config.py` 的 `DEFAULTS`。

**每一项的生效值与取值来源都能查**：`GET /api/v8/config` 会返回
`生效口径`、`取值来源`、`内置默认`、`环境变量映射` 四块内容。
改完口径先查这个，不用去猜。

## 3. 开关清单

| 开关 | 环境变量 | 配置文件路径 | 默认 | 关掉时 | 打开时 |
|---|---|---|---|---|---|
| 算法版本 | `CF_V8_ALGO` | `algorithm.default` | `v8` | — | v8 / ra-next-0.1 / v1 三选一 |
| 证据模式 | `CF_V8_EVIDENCE` | `evidence.mode` | `strict` | 恢复三档判别 | 证据不足不放行绿灯 |
| Benford 适用性 | `CF_V8_BENFORD` | `quality.benford_applicable` | 留空（未声明） | `0`→Q 不进融合表（红灯） | `1`→Q 证据记充分 |
| **Q 参与融合判别** | `CF_V8_Q_IN_FUSION` | `quality.gate_in_fusion` | `1`（保持原逻辑） | Q 只作数据质量报告 | Q 参与 48 格表判别 |
| 稳定性 bootstrap | `CF_V8_STABILITY` | `stability.enabled` | `0` | — | 附 30 次 bootstrap（+1~2s） |
| 池级模型缓存 | `CF_V8_CACHE` | `cache.enabled` | `1` | 每请求全量重算 | 15× 提速 |
| 缓存上限 | `CF_V8_CACHE_MAX` | `cache.max` | `64` | — | LRU 上限 |
| 每组样本量 | `CF_V8_POOL_N` | `pool.size_per_group` | `20` | — | 允许区间 **[2, 60]**，超出报 400 |
| 森林树数 | `CF_V8_TREES` | `forest.trees` | `60` | — | — |

### 3.1 Q 参与融合判别（本次新增，默认关）

`q_in_fusion=0` 时：

- Q 照算、照常返回在 `第一层`，**数值一个字不变**；
- 融合层把 Q 状态钉在「达标」，等价于取 48 格表在 `Q=Q_OK` 上的子表
  （R3~R6、R9、R10），**不新增规则、不改任何一格**，物理上无法分叉；
- Q 的证据等级照实记录（不假装充分），但**排除在短板计算之外**，
  否则「让 Q 退出判别」与「Q 证据不足卡住绿灯」会互相抵消，开关开了等于没开；
- Q 本身不可用时**仍按 R1 红灯**处理——第一层连数值都算不出来，
  是「门禁失效」而不是「Q 退出判别」。

返回体里会带 `融合判定.Q参与判别` / `融合判定.Q仅报告`，留痕可直接据此追溯。

**这是待业务裁决项**：Q 实测区间 [0.93, 1.0]，而融合阈值是 0.3 / 0.5（旧 χ² 尺度遗留），
意味着第一层几乎恒为「达标」。建议业务在「Q 参与」与「Q 仅报告」两条路上各跑一段时间，
看实际留痕分布再定。

### 3.2 证据模式（strict / loose）

- `strict`（默认）：证据不足 → 绿灯升黄 + 标记需人工复核；**从不降档**。
- `loose`：恢复三档判别，但复核标记仍在。

注意：只关 Q 参与判别、证据模式仍是 strict，**绿灯仍会被 P 证据不足卡住**。
要让三档判别真正恢复，两个开关要一起动。

## 4. 开关的容错约定

| 情形 | 行为 |
|---|---|
| 配置文件不存在 / 损坏 / 顶层不是对象 | 只告警，全部回落内置默认 |
| 配置文件含未知段或未知项 | 逐项告警后忽略（拼错的键不会静默生效） |
| 环境变量取值非法（如 `CF_V8_ALGO=v9`） | WARNING 后回落下一级 |
| 环境变量留空（`CF_V8_ALGO=`） | 视为**未配置**，不是 False |
| 请求参数非法 | 与算法参数错误同级，**HTTP 400**（调用方缺陷） |
| 数值超范围（`CF_V8_TREES=999999`） | 回落默认，不抛异常 |

理由：配置是运维输入，配错最多退化成默认行为，不该让评估接口 500。

## 5. 热加载

改完 `deploy/algorithm.config.json` 无需重启：每个请求都会重新读取。
缓存键用文件**内容哈希**（SHA256），而不是 mtime——
部分文件系统 mtime 粒度是秒级，且 `v8`→`v1` 这类改动字节数相同，
只比 `(mtime, size)` 会漏检。

## 6. 上线核验

```bash
# 一看生效口径与来源
curl http://127.0.0.1:8010/api/v8/config

# 二看默认路径（不传任何开关参数）与开关路径都符合预期
curl 'http://127.0.0.1:8010/api/v8/assess'
curl 'http://127.0.0.1:8010/api/v8/assess?algo=v1&q_in_fusion=0&evidence=loose'
```

前端「风险评估」分区的配置面板里也有四个对应开关，结果区会回显
「本次生效开关」与取值来源，用于确认前端以为的口径与后端实际走的一致。

## 7. 样本量上界为什么是 60

池级模型的构建随规模**三次增长**（瓶颈是 DA 的 LP）：

| 每组样本量 | 池大小 | 构建耗时 |
|---:|---:|---:|
| 20 | 40 | 0.30s |
| 40 | 80 | 1.63s |
| 60 | 120 | 6.95s |
| 100 | 200 | 39.8s |

所以 60 是硬上界：再往上既是 DoS 入口，收益也很有限。
60 刚好满足「P 层证据充分」所需的规模（每组 60 时校准集才够 30）。

注意：**请求里显式传的 `n` 也会过这个范围校验**。
配置层在超范围时确实会回落，但它管不到调用方直接塞进来的值。

留痕、确定性、并发、前端 JS 语法与元素引用。

## 9. 应急回退

把 `deploy/algorithm.config.json` 删掉（或 `CF_V8_CONFIG` 指向一个不存在的文件），
所有开关立即回到内置默认，即改造前的原有行为。
