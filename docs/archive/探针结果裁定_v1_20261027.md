## 2. 路线裁决：C 出局，B 确立

**路线 C（Pyodide/WASM 跑原 Python）——出局。**
理由：它存在的唯一价值是"避免重写"。现在已知目标环境是标准 Node v22、内存约 1GB、单次纯 CPU 计算在 10 秒内完成没问题，而待移植核心仅约 1063 行纯标准库逻辑。
为了省一次翻译，引入 WASM 运行时体积、冷启动与 xlsx 依赖不确定性，属于**用高风险换小收益**。不划算。

**路线 B（计算引擎 Node 化）——确立为唯一主线。**
支撑事实：
- Node v22.23.1 标准运行时，无需任何特殊适配；
- 包 <100KB 远低于任何合理体积阈值，包体积不是瓶颈；
- 内存约 1GB，本次计算的驻留数据量远低于此；
- 纯逻辑单次 CPU 在秒级，不触及超时与单线程阻塞风险。

## 3. 必须主动守住的一点：我们能外接，但我们不接

探针证明外网 HTTPS 完全通畅。**这意味着"挂阿里云 Python 算钱"在技术上百分之百可行。**

这恰恰把答辩 Q1 逼到了最诚实的位置：**以千问办公为核心，从此刻起不是能力受限的结果，而是一个明确的选择。** 若将来有人质疑"你们是不是因为做不到才不用外部服务器"，答案是相反的——我们测过通路，然后决定不走它。

这条要原样保留在对外口径里。

## 5. 存储的安全要点（新识别，尚未处理）

内置库经 Supabase REST + ANON_KEY 访问，而**访客是匿名的**。这意味着：

- ANON_KEY 一旦写进前端，任何人都能拿到，等于数据裸奔；**必须只留在服务端**；
- 所有写操作共用同一把 ANON_KEY，**隔离只能靠 Supabase RLS 策略**，不能靠应用层自觉；
- 因此 session/owner 字段必须进入库表并写进 RLS 条件，否则答辩 Q8 的会话隔离在数据库层直接失效。

这一条在此之前未被识别，现加入 Stage 3 的必做项。
