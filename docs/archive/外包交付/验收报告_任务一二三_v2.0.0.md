## 二、阻塞级冲突（必须先解决，否则合入即坏）

### C1 · 两个"14 工具"清单不同物（最容易骗过所有人）

程序化比对：两份清单**只有 10 个交集**。

| | 内容 |
|---|---|
| 任务一的 14 | `quality_check` `deada_score` `fuse` `run_stress_test` + 10 个存储/查询类 |
| 我们裁决 A1 的 14 | `rf_predict` `query_audit_by_event` `log_stress_test` `load_da_coefficients` `save_da_coefficients` + 10 个存储/查询类 |
| 它有我没有 | `quality_check` `deada_score` `fuse` `run_stress_test` —— **全是把计算搬进 MCP 的工具，正面撞裁决 A1（折中：Q/D/FUSE 在千问表格内）** |
| 我有它没有 | `load/save_da_coefficients`（DEA-DA 系数入库必需，缺了第二层没法版本化）、`query_audit_by_event`、`log_stress_test` |

`run_stress_test` 尤其要指出：协议 §二 明确"压力测试在千问工作台完成，MCP 只保存结果"，所以定稿是 `log_stress_test`（存已算结果），而不是让 MCP 跑压测。
**要求**：作者与指挥二选一并写进裁决；如果坚持要 MCP 计算路径，需按 v2 模型包先例申请例外并说明合规话术。

### C2 · 库名与排序规则冲突，且三张表重名

- 任务二建在 `audit_db` + `utf8mb4_bin`；我们的 `init.sql` 建在 `cf_workbench` + `utf8mb4_0900_ai_ci`。
- **init.sql 里已经存在同名 `quality_log` / `deada_score_log` / `rf_predict_log`（结构远比任务二简）**。
- 后果：先跑 init.sql，任务二必然"table exists"报错停止；先跑任务二，init.sql 的 `IF NOT EXISTS` 会**静默跳过**，留下"文档以为有 11 张表、库里实际混着两套字段"的状态。跨表按 `run_id` 关联、统计视图、幂等账本全部对不上。
- 附带：`utf8mb4_bin` 会让中文文本列比较字节化，与其余 8 张表 JOIN 文本列时可能报 illegal mix of collations。

**要求**：三张表的权威 DDL 只允许一份。建议**采纳任务二的结构**（它比我们那版严谨得多），合入 `sql/init.sql` 并把库名统一为 `cf_workbench`、排序规则统一为 `utf8mb4_0900_ai_ci`。

### C3 · 灯色词表三套并存（讽刺的是这批文件自己刚提出 I11）

| 位置 | 用的词 |
|---|---|
| 任务二 SQL 约束 | `('绿','黄','红')` |
| init.sql / 协议 | `green / yellow / red / unknown` |
| 任务一 system_prompt、任务三正文 | `红灯 / 黄灯 / 绿灯 / 待复核 / 待校验` |

三套互不兼容，`待复核` 与 `待校验` 还混用。落库比较会静默不匹配——正是 I11 的同类问题。
**要求**：定一版映射表：DB 一律 `green/yellow/red/unknown`，展示层再译成中文；"待复核/待校验"统一为一个词并明确对应 `unknown` 还是独立状态。

### C4 · 新维度 `company_id` 只加在 3 张表上

任务二引入 `company_id`（并把 `cohort_id` 与它分离，这个设计是对的），但另外 8 张表没有该列 → 同一 run 跨表按企业关联会缺列；而我们单企业演示是 `tenant_id` 固定绑定。
**要求**：明确 `company_id` 与 `tenant_id` 的语义关系，并**统一加到 11 张表**（或明确废掉、用 tenant 承担），不能三张有八张无。

## 三、工具签名违反协议红线（5 处，逐条改）

| 工具 | 任务一 required | 违反什么 |
|---|---|---|
| `verify_payment` | 含 **`status`** | 协议 §5.7 + 验收 12：状态不得由模型提交。它自己 desc 写着"status 不得由模型自行宣称成功"，却又列为必填 —— 自相矛盾。**删 status**，由服务端返回 |
| `log_exception` | 含 **`approver`**、缺 **`approval_ref`** | 协议 §5.5：只核 `approval_ref` 凭据，不信模型给的审批人姓名 |
| `save_param_template` | 含 `source`、缺 **`template_version`** | 协议 §5.4：版本不可覆盖、历史事件引用当时版本。`source` 是 v8 §8.4 已作废写法 |
| `log_to_mysql` | 只有 `event_type`+`payload`，缺 `request_id`/`source_ref`/`occurred_at` | 幂等与来源追溯三件套是协议 §四 硬要求，缺了就防不了重复记账 |
| `log_feedback` | `accuracy`/`deviation` | 定稿是 `accuracy_label`(accurate/inaccurate/pending) + `metric_code`/`evaluation_version`/`forecast_start_at`/`end_at` 等 12 项；`deviation` 不在契约内 |

另：`run_stress_test` 描述"金额统一万元"——MCP 边界要么规定**一律元字符串**（协议 §一），要么必须带 `unit` 并由服务端换算留痕；不能与 v2 模型包那个 `unit` 自由取值混用。

## 四、缺件与实现级问题

1. **缺 `supersedes_id`**：协议 §八 要求追加式纠错（不改写旧审计），三张表都没有。
2. **缺 `mcp_request_ledger`**：三表自带 `payload_sha256 + uq_*(tenant,company,run,record_key)` 幂等，与我们的账本**两套机制并存**。建议保留两套但写清分工：账本管跨工具请求幂等，`record_key` 管同 run 内逻辑行唯一；否则会出现"账本判重、表里无记录"。文档目前未写。
3. **无 GRANT / 三账号**：`cf_app` 仅 SELECT/INSERT、`cf_admin` 迁移、`cf_backup` 备份——与我们 init.sql 的授权段没接上（它 §6.5 提了"不用 root"但没给语句）。
4. **`request_id VARCHAR(64)`**：协议与 init.sql 是 1~128。严格模式下合法长 id 会报 1406 被拒（不是静默截断，但等于自断）。改 128。
5. **`ck_rf_success` 硬编码 `JSON_LENGTH(features)=30`**：与 v2 模型包 §1 结论冲突——那份交付明确"风险数字特征默认从新模型移除，仅研究折内保留"。30 维若继续硬卡，将来换特征清单会全线插入失败。建议 30 由服务端按 `feature_schema_version` 校验，DB 只保证 `features` 与 `feature_names` 等长。
6. 脚本尾部三条 `SHOW CREATE TABLE` 在批处理管道里会混出结果集，建议注释或单独执行；`TEXT/JSON DEFAULT NULL` 在 MySQL 8 可用但无意义，可删。
7. 任务一的 `system_prompt`/`schedules`/`exception_branches` 是自定义结构，**没有"本设计字段 → 千问实际配置项"映射表**（它自己在 deployment_blockers 承认了）。补这张表才算能落地。
