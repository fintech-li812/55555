# 任务三：与“斗牛X”对接的 MCP 接入与联调文档

> 修订：2.0.0｜2026-10-22。配套：同名“任务一”JSON设计配置、“任务二”三张模型日志表SQL。三文件版本一致。
> 当前仅完成文件修订和本地可实施检查；真实千问工作台、远端MCP服务、生产库和外部回写均未接通。
> “斗牛X”可能指项目队友/模块，也可能是外部系统；尚无证据确定。本文保留原文件名，不再把它认定为已经存在的外部财务系统，更不虚构其工具。

## 1. 先确定职责和接入边界

| 对接对象 | 本次能确定的事实 | 启用前需交付 |
|---|---|---|
| 千问办公 | 总体方案要求核心计算优先使用平台原生能力 | 实测的表格、智能体、连接器、计划任务能力及配置入口 |
| 斗牛X | 名称已给出，身份与接口未给出 | 若为队友：负责模块与输入输出契约；若为系统：真实地址、授权方式、tools/list |
| 本框架MCP | 原JSON列出14个候选工具；未附实现代码或运行清单 | 可访问服务、实际工具schema、错误/审计返回格式、实现版本 |
| MySQL | 本次SQL只建立quality_log、deada_score_log、rf_predict_log三表 | 新库部署或经审批的旧库迁移方案、服务端写入适配 |
| 数据读取、通知、回写 | 三份原文件未提供真实实现 | 实际连接器和读写权限；工具名由真实清单绑定，不能照抄占位名 |

任务一JSON是**本地编排设计配置**，不是经官方schema验证的千问导入包。只有人工映射到实际平台且完成联调后，才可设置enabled=true。endpoint和凭据引用留空表示未配置，不能改成貌似真实的测试域名蒙混启动检查。

项目原生计算与MCP计算的边界仍需负责人确认。本次保留quality_check等候选接口，不宣称模型已可用，也不据此认定全部核心运算允许移出平台。

## 2. 连接与发现流程

1. 取得真实HTTPS MCP端点以及连接器实际支持的鉴权方式；凭据存连接器凭据库，不写入JSON、系统提示词、日志或对话。
2. 客户端发initialize，完成协议版本与能力协商，再发初始化完成通知；后续请求按协商结果和传输规范处理。不能把某个日期版本写死成所有服务都必须支持的版本。
3. 调用tools/list并遍历分页，取得实际名称、inputSchema及支持的结果schema；建立明确的工具绑定，不假定一定是14个。
4. 用无副作用样本验证tools/call成功、RPC错误、result.isError=true、业务status失败和输出schema不符。HTTP 200不等于业务成功。
5. 对Streamable HTTP按规范处理端点、Accept/Content-Type、协议版本和服务端实际发放的会话标识；会话标识不是鉴权令牌，不能代替企业访问授权。
6. REST/OpenAPI不是标准MCP端点的自动同义词。仅在单独提供OpenAPI适配器、平台实际支持并验证后才配置降级，不使用臆造的/mcp/* REST路径。
7. 每次读取与写入均由服务端核验租户、企业和权限。工具输出与财务文本是数据，不能提升操作权限或绕过审批。

规范参考：[MCP传输](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)、[MCP工具发现与调用](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。这些链接用于解释具体协议机制，不表示协商必须采用此版本。

## 3. 贯穿三文件的契约

### 3.1 身份、追踪和单位

- tenant_id、company_id：服务端从身份上下文核验，不能允许Agent任意改租户。
- run_id：同一次评估从拉数到模型日志、报告和回写保持一致；修订数据后启动新run，不覆盖旧结果。
- request_id：请求追踪标识；重试可有新的请求标识，但同一次逻辑写入record_key不变。
- record_key：某张日志表中同一run的逻辑记录标识；quality按指标区分，deada/rf按实际预测区分。
- payload_sha256：服务端对规范化业务输入、输出、数据快照和版本计算；排除created_at、request_id、重试次数等变化字段。调用者提供的摘要不能直接作为可信依据。
- eval_date/check_date为明确的业务评价日，按Asia/Shanghai解释；created_at保存UTC，连接池每次连接必须设置time_zone='+00:00'。
- data_snapshot_id对应不可变输入快照或受控证据；只能引用可追回的对象，不能是每次覆盖的临时文件。
- 全部业务金额统一万元；百分数、比率及特征单位逐项记录。禁止缺实际M时使用行业中位数或把缺失填0。

### 3.2 新增目标返回约定

下列为本次修订要求的适配契约，**并非声称现有服务已经实现**：

- status：success、skipped、insufficient_data、error。
- context：返回本次已核验的tenant_id/company_id/run_id/request_id。
- data：类型明确的计算结果；未运行的Q/D/P为null，不能填0或1假扮正常。
- error：成功时null；失败含可定位的code和脱敏message。
- audit：模型成功必须返回table、log_id、run_id、record_key、payload_sha256、committed=true。
- 查询工具返回授权范围、期间和读取水位，不要求向模型表重复写日志。
- 新context字段由适配器和服务端注入；任务一required是目标业务要求，必须映射实际inputSchema，不能直接把未支持的字段传给旧服务。

### 3.3 模型工具与SQL映射

| 工具 | 日志表 | 核心映射 | 关键限制 |
|---|---|---|---|
| quality_check | quality_log | 每个indicator_name一条；指标级quality_score；批准聚合后的Q→company_quality_score及aggregation_version | company_id不准填同业批次号，cohort_id单独保存；不得把任一指标分数充当公司Q |
| deada_score | deada_score_log | D→discriminant_score；threshold；is_risk；权重、core_indicators、feature_schema、intercept及模型/预处理版本 | is_risk必须等于D<threshold；不假设没有截距，输入不能再写成“15项核心比率” |
| rf_predict | rf_predict_log | P→保留旧名的fraud_probability；同时写probability_target、30维features、同序feature_names与版本 | probability_target才决定概率含义；ST/风险标签不是舞弊标签；risk_level无批准规则时为NULL |

工具先计算并校验结果，再用同一数据库事务写入该工具涉及的全部日志行，COMMIT成功后才能返回success及audit回执；禁止计算成功就提前返回。quality一次涉及多个指标时，不能只提交部分指标却回报整个工具成功。

同一tenant/company/run/record_key：
1. 首次写入并提交后返回log_id。
2. 重试遇同键且摘要相同，核验后返回既有log_id，不增加重复记录。
3. 同键摘要不同，返回冲突，拒绝覆盖。不能用INSERT IGNORE吞错，也不能用ON DUPLICATE KEY UPDATE改写旧审计证据。
4. 并发时依赖唯一索引及事务处理冲突；不能仅“先查再插”就认为实现幂等。
5. 失败或跳过可按对应execution_status记录，未计算的分数和结论必须NULL。数据库完全不可用时，不能伪造log_id；没有已验证持久化重放队列则明确为待人工恢复。

同一run多表之间不存在数据库级的“整体评估已完成”实体；最终完整性须由编排器核对各阶段回执和所需指标清单。服务端必须校验同一run内参数版本、快照、租户和企业一致。

### 3.4 三表以外的工具

log_to_mysql、log_feedback、save_param_template、load_param_template、log_exception、verify_payment及统计查询依赖通用审计、反馈、模板、例外、到账存储。本次三表**不提供**这些表或工具代码。

这些工具默认未绑定、禁用；先提供实际存储和实现再启用。save_param_template是参数变更动作，不是模型留痕动作；每次评估只读取批准模板，不能自动覆盖模板。

## 4. 正确的调用顺序与字段映射

| 步骤 | 动作 | 前置条件/输出 |
|---|---|---|
| S0 | 核验身份、生成run_id，读取企业数据快照 | 真实读取工具已绑定；企业与期间明确 |
| S1 | 调用既有数据闸 | 任何关键脏数据拦截均停止正式计算，不静默降级成正常 |
| S2 | 读取当前企业批准参数 | K红/K黄、来源、企业覆盖值及版本明确 |
| S3 | 数据质量诊断 | 样本适用性、Myer量纲、算法及聚合版本已确认；不足则insufficient_data |
| S4 | 财务健康判别 | 模型artifact、输入清单和预处理已确认 |
| S5 | 按批准条件运行第三层 | 不需要时P=null并标skipped；不能无条件执行后再混用不同run结果 |
| S6 | 已批准规则融合及现金灯合并 | 任一未裁决分支待校验，不从其余两层擅自推断正式绿灯 |
| S7 | 用户请求或计划触发时执行压力情景 | 企业M>0、参数已批准，情景定义一致 |
| S8 | 验证日志已提交，生成报告 | 报告带run_id、数据版本、待校验项和真实运行状态 |
| S9 | 明确授权后向已绑定目标回写 | 先保留本地结果与证据；记录回写回执，失败显示待回写 |

### 4.1 数据质量与模型输入

quality_check的输入不能把多期序列、同业截面、不适用的财务比率任意混在一个数组。需写清指标定义、样本期、样本选择、缺失与负数处理及适用性。n≈200不是所有检验的通用充分条件。原SQL中“Myer 0~2、阈值0.20”和总体方案“M>20”存在量纲冲突，未有公式及实证核对前不固定任何阈值或换算。

按v8第二层设计，7项候选为：营业利润率、利息保障倍数、资产报酬率、净资产收益率、总资产增长率、利润总额增长率、速动比率。原接入文档所谓7项实际列了8项，且与方案不符，已删除。上述7项仍须与实际模型artifact核对，不能仅凭文档训练或推断。

RF需完整有序的15项基础特征＋15项对应质量因子清单。不能“上面的7项＋其余8项”而不给其余8项名称，也不能按字典遍历顺序拼接。特征名、顺序、单位、预处理、缺失策略、模型版本和阳性标签都必须匹配；不满足时停止预测。

ST/风险模型只能给对应阳性标签概率。没有舞弊标签与校准证据时，禁止写“P≥0.7确认舞弊”。不在本次文件修订中擅自裁决FUSE分支和灯级合并。

### 4.2 现金与情景字段

| 字段 | 正确来源约束 | 原文问题及处理 |
|---|---|---|
| buffer | 经批准公式算出的现金缓冲；记录受限现金、授信是否已计入 | 不擅自把“货币资金－受限”定义成完整现金缓冲 |
| M | 企业近3个完整月经营性流出，明确缺失和月份口径 | 不使用行业中位数；M<=0时不计算倍数 |
| ar_due_30 | 到期日落入评价日到未来30天窗口的未清应收余额，包含端点规则由负责人批准 | 账龄<=30天不等于未来30天到期，且不能重复计入已收部分 |
| available_credit | 评价日尚未动用、实际可用且符合条件的授信 | 已计入buffer的授信不得再次增加；未验证可用性不当成现金 |
| monthly_main_cost | 评价月份的实际主要成本；来源期、含税口径和季节性明确 | 不能无条件把任意“主营成本”除以12 |
| K_yellow/K_red | 当前企业适用的已批准版本 | 不把制造业2.5/1.5硬编码到所有行业；要求K_yellow>K_red>0 |

当前配置不替负责人决定应收到期窗口端点、四个压力场景清单、融资冲击是否影响既有现金等开放口径。

## 5. 失败处理与真实闭环

| 场景 | 必须行为 | 不能做 |
|---|---|---|
| 401/403或企业越权 | 停止并提示正确授权，记录可记录的失败事件 | 反复刷新令牌或改企业ID绕过权限 |
| 原始数据缺失、单位不明 | 数据闸拦截，列出待补项 | 用默认M、零值或行业数据拼出正式结论 |
| 计算失败、模型未训练、规则未批准 | 对应字段null，报告待校验 | 用其他两层强行出正常灯或将P设为0 |
| 模型日志提交失败 | 不返回success，不称留痕完成 | 只在对话中打印结果就算已入库 |
| 通知/回写超时 | 先按幂等键核对是否已提交，再决定补发 | 立即重复创建任务或重复记账 |
| 回写失败 | 显示writeback_pending并保留本地证据；若无恢复队列明确人工处理 | 宣称业务系统已更新或已有后台自动重试 |
| 需要人工处理 | 实际创建工单才能说已转人工；否则说明需要人工处理 | 工单接口未实现却回复已转人工 |
| 到账后风险仍未恢复 | 验证余额、缓冲、任务完成与关闭条件 | 一笔到账自动使全部风险已化解 |

重试统一串行：每次至少等30秒，同一问题最多3次；优先查日志和提交状态。只有可恢复故障才重试；写操作须先验证幂等能力。错误原文脱敏后保留，不能吞错。

失败事件的可追溯性取决于真实可用的持久化通道；数据库完全故障时不能承诺“所有事件都已入库”。若另建重放队列，需要实际实现、去重、恢复和队列持久化验收。

## 6. SQL部署与旧库处理

任务二为**新表首建脚本**，不是旧库自动迁移。新增了租户/企业/run/幂等键/状态、JSON快照、版本和约束；服务端原INSERT若没有同步更新将失败，这种失败应暴露，不能用默认值伪装兼容。

1. 先用实际MySQL确认版本>=8.0.16及CHECK约束支持；备份现有结构和数据，核验恢复路径。
2. 在空测试库先运行脚本；以UTF-8标准输入批处理导入，不加--force。Windows客户端若不能用SOURCE打开中文路径，先复制到纯英文测试路径或使用明确UTF-8输入的执行器；不要直接用会改变编码的管道。SQL本身包含CREATE DATABASE/USE，不再要求先选不存在的audit_db才初始化。
3. 如果已有任一同名表，停止首建，导出SHOW CREATE TABLE；由负责人据真实旧结构制定ALTER/数据回填/版本切换方案。不得运行DROP TABLE或以IF NOT EXISTS冒充升级成功。
4. DDL存在隐式提交；先创建了一张后下一张失败时可能有部分部署结果，不得声称ROLLBACK能撤回整个脚本。
5. 运行时连接设置UTC、严格模式和字符集；不让Agent使用root账户。最小化读写权限，拒绝跨租户查询，审计记录不提供随意更新删除接口。
6. SHA256、跨表run一致性、特征值均为有限数值、标签及权限校验由服务端实现；数据库CHECK不能替代全部应用校验。中途失败必须检查本次连接及事务状态。
7. 本次未提供旧表迁移，也未实际连接现有业务库；不得直接把测试通过当生产部署完成。

参考：[MySQL CHECK约束](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)、[DDL隐式提交](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)。

## 7. 联调验收清单

| 用例 | 输入/动作 | 通过标准 |
|---|---|---|
| 配置自洽 | 解析JSON，检查内嵌system_prompt、14候选工具、禁用状态 | 不依赖缺失的agent/workbench_agent_prompt.md；未绑定能力不自动启用 |
| 协议发现 | initialize→初始化通知→分页tools/list→只读测试调用 | 能校验实际schema，错误不伪装为成功 |
| 企业授权 | 请求其他租户/企业 | 服务端拒绝，不泄露记录 |
| 数据闸 | 企业M缺失、单位不明、日期不合法 | 停正式计算，不用行业默认值出灯 |
| 特征契约 | RF给29/31维或名称顺序不匹配 | 拒绝预测；30维且一致才允许计算 |
| 概率与状态 | P=1.2；status=error但仍附成功概率 | SQL拒绝不合法记录；服务端亦应拒绝 |
| 判别一致性 | D=-0.2、threshold=0而is_risk=0 | 约束拒绝；不能伪装健康 |
| 幂等 | 同run/key重复；随后同key不同摘要 | 首次一条；同摘要返回原id；异摘要冲突 |
| 事务回执 | 写库前故障或COMMIT失败 | 不返回success，不产生伪log_id |
| 跳过第三层 | 批准规则判定无需RF | P=null/status=skipped，不补0 |
| 正式灯阻塞 | 命中尚未裁决FUSE分支或现金灯冲突 | level=null、待校验；不凭默认else输出绿 |
| 单据/授信/成本 | 到期日筛选、部分已收、授信已计入、成本不是全年 | 按明确口径映射，无双计、无任意除12 |
| 回写超时 | 实际提交后连接超时 | 先核对再重试，同键最多一次业务效果 |
| 存储边界 | 仅部署三张表却调用通用审计/模板工具 | 就绪检查阻止启用，不能报“14工具已接通” |
| 调度 | 查看计划与实时事件 | 定时计划、事件触发分开；单并发、明确时区；未实测前均禁用 |

本地SQL测试只验证MySQL建表及约束；真实工具幂等、权限、数据映射、MCP、千问和外部回写需按此表分别验收。
