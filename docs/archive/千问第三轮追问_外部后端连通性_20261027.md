# 千问第三轮追问：外部后端连通性验证

日期：2026-10-27 傍晚。用途：验证「前端挂千问、后端放自有服务器」这条架构能不能真的连起来。
性质：**纯验证任务书**。粘贴给千问执行，把原始结果回传给我。

---

## 0. 已确认的事实（本轮不再重复问）

- A2：用自己的 Key 调外部模型 → **不算破线**，AI 可以接。
- D4：动态网页挂数据库 → **必须个人标准版付费**，免费档挂不了。
- 讲座口径：外接所有东西都可以，只要网页是在千问办公上完成的（"甚至包装一下就行"）。
- 探针已实测：千问**服务端**能出网（npm registry 1422ms、阿里云 57ms 均 200），网关单次请求上限 30 秒。

---

## 1. 背景（一句话）

我们可能把后端、Agent、工作流、数据放在自己的服务器上，千问这边只保留前端页面。
**所以必须确认：页面能不能把请求送出去、以及能不能送回来。**

---

## 2. 要验证的四件事

### G1｜浏览器能不能直接访问外部域名（CORS / 混合内容 / CSP）

这是方案 A 的命门。注意区分两件事，别混为一谈：
- 探针 V1/V2 证明的是**服务端**能出网；
- 这里要测的是**页面里的浏览器**能不能出网——两回事，浏览器受 CORS 和 CSP 管。

**做法**：在探针页放一个按钮，点击后用 `fetch()` 请求下面两个地址，把结果原样显示在页面上：

```
https://httpbin.org/get        （公开测试接口，允许 CORS）
https://api.github.com/zen     （另一个公开接口）
```

**要回传的原始结果**：
- HTTP 状态码，或浏览器控制台的完整报错原文（CORS 报错、mixed-content 报错、CSP 报错的原文都不一样，必须原样给我）；
- 如果成功，返回体的前 200 字符。

### G2｜Node 后端转发外部请求（这条路理论上必然可行，验证一次并测延迟）

**做法**：在探针页后端加一个 `/api/relay?url=...`，服务端用 https 去取外部地址，把状态码、耗时、前 200 字符返回。

**要回传**：两次调用的结果（目标用上面那两个地址），含 `latency_ms` 与 `status`。

**为什么还要测这条**：即使 G1 被拦，只要 G2 通，架构就成立——前端请求自己的 `/api/*`，由千问 Node 后端转发到我们的服务器。**G2 是保底路径，必须确认它的真实延迟**，因为它决定了页面响应速度。

### G3｜千问办公的 Skill / MCP 能不能被外部服务器调用（最关键，答不出就是没有）

这是整套架构里我最没把握的一环。请如实回答，不要推测：

1. 桌面端的 Skill / MCP，是不是只在本机进程内可用（比如 stdio 方式）？
2. 有没有**对外可调用的 HTTP 端点 / 云端 API / 远程 MCP 入口**，让我自己的服务器能调到你这边的 Skill 或 MCP？
3. 如果有，鉴权方式是什么（API Key / OAuth / 其他）？在哪里能看到文档？
4. 如果没有，**请直接说"没有"**——这个答案同样有价值，我不会怪你。

> 这条决定我们的后端到底是不是"在调用千问的能力"。
> 如果答案是"没有"，那我们后端就是纯自有系统，跟千问的关系只剩"前端托管在你这儿"，我会如实调整架构描述，不会对外声称在调用千问能力。

### G4｜页面的响应头里有没有 CSP 限制

**做法**：返回探针页 HTML 与 `/api/*` 的完整响应头，我要看有没有 `Content-Security-Policy`，特别是 `connect-src` 这一项。

## 3. 红线（必须遵守）

1. **不要挂载数据库**——本轮纯验证，不碰不可逆操作。
2. **不要写真实企业数据**——只用上面两个公开测试接口，不传任何业务数据。
3. **不要把密钥写进前端**——G2 的 relay 不要带任何 Key。
4. **用现有的探针页迭代**，不要新建页面、不要动其他 Page。
5. **不要替结果伪造成功**——被拦就是被拦，把报错原文给我，不要写死 `"ok": true`。
6. 如果某项做不到，**直接说做不到**，不要给推测性结论。
