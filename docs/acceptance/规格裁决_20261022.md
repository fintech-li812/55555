# 规格裁决 2026-10-22（D8—D13）

> 承接 `规格裁决_20261021.md`（A1—A7）。本轮起因：队友交付的《任务一 Agent 配置 / 任务二三张模型日志表 SQL / 任务三 MCP 接入文档》(v2.0.0) 与已定稿的 `sql/init.sql`、MCP 协议发生库名、表结构、枚举与工具清单四处冲突。
> 状态：指挥拍板，即刻生效。**服务器侧与 DDL 一律以本文件为准。**

| # | 议题 | 裁决 | 理由 |
|---|---|---|---|
| **D8** | 库名与排序规则 | 统一 **`cf_workbench` + `utf8mb4_0900_ai_ci`**；弃用 `audit_db` 与 `utf8mb4_bin` | 同库混排序规则会在跨表 JOIN 文本列时报 illegal mix of collations；`_bin` 还使中文枚举值比较字节化，与 D10 的中文展示词冲突 |
| **D9** | 三张模型日志表的权威 DDL | **采纳队友"任务二"的结构**（租户/企业/run/record_key/payload_sha256/execution_status/JSON 快照/版本/全套 CHECK），合入唯一一份 `sql/init.sql`；同时补 `supersedes_id`、`request_id` 改 VARCHAR(128)、并保留 `mcp_request_ledger` | 它比我们原三表严谨得多（NULL 而非默认 0、成功才须有值、跨字段一致性 CHECK）。两套幂等机制分工：**账本管跨工具请求幂等，`record_key` 管同一 run 内逻辑行唯一** |
| **D10** | 灯色枚举 | 库内与协议一律 `green / yellow / red / unknown`；中文（红灯/黄灯/绿灯/待复核）只存在于展示层；**"待复核"与"待校验"合并为一词，对应 `unknown`** | 现已并存三套词表，SQL 约束存 `'绿','黄','红'`、init.sql 存英文、文档存中文。这正是队友自己提的 I11（字符串后缀漏匹配）的同类病 |
| **D11** | MCP 是否承担计算 | **维持裁决 A1**：不设 `quality_check`、`deada_score`、`fuse`、`run_stress_test` 四个 MCP 工具；补齐 `load_da_coefficients` / `save_da_coefficients` 与 `log_stress_test`（保存已算结果，不在 MCP 跑模型）。工具数仍为 **14** | 核心判定留在千问表格内，这是 v8 §1.4 合规依据与答辩主线的支点；出现"第二套 14 工具"是最容易被误认成一致的事故源 |
| **D12** | 金额单位 | MCP 边界与库内一律**元**（十进制字符串，DECIMAL(20,2)）；万元只允许存在于千问表格与看板展示层，接入层显式换算并留 `unit` 痕迹 | 协议 §一 原文；也防制造业那格"万元列填元值"（1631300）被二次放大 10⁴ 倍 |
| **D13** | RF 特征维度校验 | 删除 `CHECK (JSON_LENGTH(features)=30)`，改为 `features` 与 `feature_names` 等长即可；30 维是否成立由服务端按 `feature_schema_version` 校验 | 与《现金流风控 v2》结论冲突——那份交付明确"风险数字因子默认移出特征、仅在研究折内保留"，硬卡 30 会让换特征清单时全线插入失败 |

## 追加 D14—D16（同日，回答 workbuddy 的远程访问三问）

| # | 议题 | 裁决 |
|---|---|---|
| **D14** | 远程访问方式 | **只用 SSH 隧道，3306 与 8000 均不开公网、安全组不放行这两个端口**。人的访问走 `ssh -L`，千问连接器访问 MCP 也走 `ssh -L 18000:127.0.0.1:8000`。协议 §3.3「MySQL 不对公网暴露」是硬约束；公网 IP 白名单会因队友 4G/家庭带宽变 IP 而逐步退化成 `0.0.0.0/0` |
| **D15** | 成员账号形态 | 按**角色**建，不按人建：`cf_admin`（迁移发布，仅包A+牛马Y）、`cf_read`（只读，牛马X/包B 查数）、`cf_app`（应用机账号，仅 SELECT/INSERT，localhost）、`cf_backup`（备份机账号，localhost）。**不设 dev 读写人用账号**——审计表是追加式设计，人员手工 UPDATE/DELETE 会破坏 `supersedes_id` 纠错链。人的身份在 SSH 层用公钥区分，MySQL 层只留角色 |
| **D16** | 服务器性质变更 | 实际为**阿里云主机**（此前记为局域网自有机）。连带修改：`部署手册.md` 拓扑与 §5 偏差登记（现在确实是公网主机，SSH 是唯一放行端口，HTTPS/令牌的紧迫性上升一档）；v8 §八「局域网自有设备」表述改回「云服务器」；`§十二 成本表`「云服务器 0 元」不再成立，需填 ECS 实付月费与带宽 |

| D19 | pymysql | **授权安装**：只装进 `/opt/cf-mcp/venv`，写入 `requirements.txt` 锁版本；禁止装进系统 Python |
| D20 | pip 信任策略 | **禁止常态化 `--trusted-host`**（等于关闭传输校验，是供应链风险，而这些包要装进承载审计写入的进程）。改走 `https://mirrors.aliyun.com/pypi/simple/` 或 pypi.org（实测 HTTP 200 可达）；离线安装时逐包核对 sha256 后用 `--no-index --find-links` |
| D21 | **DATETIME 默认值时区缺陷**（我在复核报告时新发现） | 服务端 `time_zone=SYSTEM`、`system_time_zone=CST`，而 DDL 里 `created_at DATETIME(6) DEFAULT CURRENT_TIMESTAMP(6)` 会按**会话时区**取值——人类用 root/admin 会话插入就会静默写成 CST，违反"库内一律 UTC"。修法：默认值改 `DEFAULT (UTC_TIMESTAMP(6))`（8.0.13+ 支持表达式默认值），并把全局 `time_zone` 显式设 `'+00:00'` 作纵深防御 |
| D22 | 依赖版本漂移 | 服务器实下为 scikit-learn **1.9.1** / numpy **2.5.4**，而模型包验证环境是 1.9.0 / 2.5.1。推理结果跨版本不保证一致：**按 requirements 精确锁 1.9.0/2.5.1**，并把 `model_version` 与实际库版本一起写入 `rf_predict_log` |
| D23 | 内存 | 1.7Gi 总量、可用 ~832Mi，已用 908Mi（含 mysqld）。要求：显式 `innodb_buffer_pool_size=256M`、`max_connections=20`、swap 由 1G 升 2G、sklearn 懒加载且 `n_jobs=1`；并报告这台机器上还跑着什么服务及其常驻量 |
| D24 | 对外 HTTPS / ICP | **本阶段不做**：全员与千问连接器都走 SSH 隧道（D14），不依赖域名与备案。`workbench.example.com` + Let's Encrypt 证书作为将来开放外部演示时的备选；备案状态核实挂账，不在本轮 |
