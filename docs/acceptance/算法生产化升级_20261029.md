## 2. 缺陷清单（问题 → 证据 → 改进 → 验证）

### A 类：可迁移性与工程结构

**A1. 研究代码在目录外根本无法调用**
- 证据：`python -c "import algo.RA_NEXT.reference as r; r.deada(...)"` → `ModuleNotFoundError: No module named 'certified_lp'`。原因是 `from certified_lp import solve` 是隐式同目录导入，只有把 `algo/RA_NEXT` 当 cwd 才成立。
- 改进：全部改为包内相对导入（`from .validation import ...`），生产包零依赖研究目录，`algo/` 以后删掉也不影响线上。
- 验证：`test_portability` 用子进程在 `~` 目录下 import 并调用，断言 D=0.187676。

**A2. 用 `exec(inspect.getsource(baseline.deada))` 重编译基线源码**
- 证据：`algo/RA_NEXT/reference.py:diagnosed_deada` 把基线函数的源码取出来，塞进一个打过补丁的命名空间重新编译执行。基线一改签名或闭包引用，结果会**静默变成错的而不报错**；打包成 pyc-only 时直接失效。
- 改进：删除该机制，DEA-DA 在本包内直接实现，自包含。
- 验证：三个 D 锚点逐位一致 + `test_deada_objective_certified`。

**A3. 生产曾依赖研究目录**
- 证据：生产适配层曾计划 import `algo/RA_NEXT/reference.py`；研究目录里混着 25 个 JSON 证据、历史快照和 6 个一次性脚本。
- 改进：生产包只依赖标准库与 `v8.indicators`，可在任意位置 import。

**A4. 职责不分**
- 改进：拆成 8 个模块，算法层只出数值，政策层负责把数值变成灯色——改阈值不再等于改模型。

### B 类：正确性与数值

**B1（本次新发现）基线单纯形遇到冗余约束直接判失败**
- 证据：题目 `max x, s.t. x=1, 2x=2` 显然有解 `x=1`，但 `layers._simplex` 返回 `(None, None, False)`。原因是人工变量留在基里、该行又找不到可换入的原变量时，代码直接 `return None`，没有删掉冗余行。
- 影响：DEA-DA 的归一化约束在退化情形下会让整题判失败 → D 降级 → 融合层按"D 不可信"处理。
- 改进：`solve_verified` 优先走基线路（保锚点）；基线路失败时由独立求解器接管，且**必须持有对偶证书才采纳**，返回体 `solver` 标注 `independent_fallback`，证据层据此把 D 记为「不足」而不是「充分」。
- 验证：`test_redundant_row` 断言 ok=True、目标=1、solver 含 fallback。

**B2. X10 ≤ 0 时用 999 天哨兵值继续算**
- 证据：`indicators.ar_days` 在 X10 非正时返回 999。这个 999 会进入 DEA-DA 的投入项，等于**用假数据算真结论**。
- 改进：X10 非正 → 该层直接不可用，不产生判别得分。
- 验证：`test_bad_data_returns_unavailable` 断言 reason 含 X10。

**B3. 只有原始可行性检查，没有最优性证书**
- 证据：ra-next-0.2 只验残差/非负/目标一致性并显式声明 `optimality_verified=false`；v0.3 补了证书，但与其他缺陷捆绑，无法单独采纳。
- 改进：独立实现两阶段 Bland 单纯形 + 对偶恢复（`Bᵀy=c_B`）+ 原始可行/对偶可行/对偶间隙/非负性四项核验。判定依据是**两条 pivot 路径给出同一目标值 + 独立路径持有证书**。
- 验证：DEA-DA 实算目标差 < 1e-7；`test_known_optimum` / `test_negative_rhs` / `test_infeasible` / `test_unbounded` / `test_certificate_rejects_nonoptimal`。

**B4. P_raw 精度被截到 4 位**
- 改进：保留 6 位（末位信息不丢）；最终 P 仍按历史口径 4 位输出，锚点不变。

**B5. 校准质量只有 Brier，没有 ECE**
- 改进：新增 ECE（等宽分箱，按箱内 |平均预测 − 实际正例率| 加权），与 Brier 一起进 OOB 报告。

**B6. 稳定性函数把 LP 解了两遍**
- 改进：合并为一次 fit + score，并把默认对偶验证关掉（探索性指标不需要证书）。

### C 类：边界与异常处理

**C1. 参数错误与数据问题混为一谈**
- 旧状：有的地方对非法参数抛异常，有的地方把非法数据当 0。
- 改进：契约化。**参数错误**（alpha=1.5、n_trees="60"）→ 抛 `ValidationError(code, field)`，这是调用方缺陷，必须修调用方；**数据问题**（缺指标、NaN、样本不足）→ 返回 `available=False + reason`，业务事实不值得崩溃。
- 验证：`test_bad_params_raise` 与 `test_bad_data_returns_unavailable` 分列。

**C2. 布尔值被当成数值**
- 证据：`isinstance(True, int)` 在 Python 为真，`True` 会当 1 参与 z-score 与树分裂。
- 改进：`is_number` 显式排除 bool、None、字符串、NaN、Inf。

**C3. 输入只报第一个问题**
- 改进：逐项扫描，一次把全部问题列出（缺 3 个指标就列 3 个），减少往返。

**C4. HTTP 层一律 500**
- 改进：参数错误 → 400 + `{"code", "field"}`；服务端故障 → 500 且记 `LOGGER.exception`。
- 验证：HTTP 实测 `trees=0 → 400 invalid_argument`。

**C5. 受评对象传错形态会"能跑但全不可用"**
- 证据：`TARGET_SCENARIOS[k]` 是带 `values` 的包装对象，某些路径只认裸的 15 键字典；传错时不会报错，只会整条链不可用。
- 改进：`assess` 自动识别两种形态。

**C6. 幅度上限未拦截**
- 改进：|x| > 1e100 直接判不可用（防 z-score / LP 溢出）。

**C7. 空池 / 类别缺失 / 树数为 0**
- 改进：全部显式返回不可用 + 原因，且不落到"看起来正常的 0"。
- 验证：`test_tiny_pool_degrades_explicitly`（n=2 时 Q/D/P 全 None 且最终不是绿灯）、`test_never_raises_on_garbage`（30 组垃圾输入 + 10 组任意池，不抛异常）。

### D 类：性能与资源

**D1. 每请求重算全部池级计算**
- 证据：单请求 0.26s 里，MC 检验 + LP + 60 棵树 + 校准**全都只依赖样本池**，与受评对象无关。
- 改进：训练/打分分离，池级产物进 LRU 缓存（键 = 池指纹 + 树数 + alpha + 模拟次数 + 验证开关）。
- 实测见 §4：稳态 **0.2675s → 0.0179s**。

**D2. 缓存无上限**
- 改进：LRU 64 条，超限时淘汰最久未用；稳定性结果单独 32 条缓存。

**D3. 并发策略**
- 取舍：构建**刻意不加锁**。构建是输入确定的纯函数，并发重复构建只浪费一次 CPU，不会产出不一致结果；加锁反而让 8 个并发请求串行等 1.3 秒。
- 实测：8 线程 × 10 次共 80 次调用，总 1.365s，缓存命中 91 / 未命中 2（启动期的重复构建），稳态后单次 0.018s。

**D4. 内存**
- 实测：单个池级模型约 **76 KB**（60 棵树 + 权重 + 校准参数），64 条缓存满负荷约 5 MB 上限。
- MC 零分布缓存 64 条 × 1999 浮点 ≈ 1 MB。

**D5. 稳定性接口**
- 改进：默认关闭；开启时结果按（池, 受评对象）缓存，且不做对偶验证（探索性指标不需要证书）。

### E 类：决策语义

**E1（最关键）证据不足不许降档**
- 证据：ra-next-0.3 把 `p_reliable = calibration_reliable`，校准集只有 10 例时 P 被视为不可用而从融合输入摘除。后果：`risk` 场景（D=−0.471、P=0.967）从 **红灯降为黄灯**。同一个"证据缺失"原则，在 `unified_view` 里是"绿灯升黄"，在 `fuse` 里是"红灯降黄"，自相矛盾。
- 改进：**只升不降**。P 数值照常进入融合表（保留它触发红灯的能力），证据不足只做两件事：绿灯升为黄灯、标记需人工复核。
- 验证：`test_insufficient_evidence_never_downgrades` 断言 P 样本充足=False 且最终仍是红灯。

**E2（最关键）不再默认全员红灯**
- 证据：v0.3 默认 `benford_applicable=False` → Q 按缺失入表 → 三个场景**全部 R1 红灯**，零区分度。
- 改进：三态语义——`None`（默认）Q 进表且证据记「不足」；`True` 证据「充分」；`False` Q 不进表（后果是红灯，调用方必须显式选择）。
- 验证：`test_benford_true_keeps_value` / `test_benford_false_drops_q`。

**E3. 48 格决策表被复制的风险**
- 改进：生产包直接 `from .. import fusion; fusion.fuse(...)`，全仓库只有一份实现，物理上无法分叉。

**E4. 顺序问题**
- 改进：证据上档在**与缓冲维度取严之后**统一做一次。若先上档再取严，缓冲维度会把证据不足的绿灯留成绿灯。

### F 类：可观测性

**F1. 无日志**
- 改进：结构化 logger（`v8.algorithm.*`），记录模型指纹、池规模、Q/D/P、规则 ID、证据等级、耗时。**只记录派生分数，不记录原始财务比率**（敏感数据不入日志）。

**F2. 无运维指标**
- 改进：`/api/v8/health`（存活 + 算法列表 + 缓存命中率）、`/api/v8/algorithms`。

**F3. 无输入输出契约文档**
- 改进：每个模块顶部写清契约，包 `__init__` 写明职责矩阵与"参数错误抛异常 / 数据问题返回不可用"两条红线。

## 5. 上线建议与回滚

**当前默认仍是 v8，本次改动不会改变线上任何输出。** 切 v1 前需要业务确认两件事：

1. **Q 尺度错位**：Q 实测区间 [0.93, 1.0]，而融合阈值是 0.3 / 0.5。切 v1 后第一层门禁不再起判别作用（这是旧尺度遗留，不是新引入的）。
2. **默认配置没有绿灯**：证据不足时绿灯升为黄灯。默认配置下 Q 证据恒为「不足」（Benford 适用性未论证）、P 证据恒为「不足」（40 例池只有 10 例校准集），因此不会有绿灯。**保留了一档判别（红 vs 黄）**，且都带复核标记。

两个开关（前端已暴露，接口可直接传）：

| 需求 | 做法 |
|---|---|
| 恢复三档判别 | `evidence=loose`（复核标记仍在，只是不升档） |
| 让 Q 证据变充分 | 业务论证 Benford 适用性后传 `benford=1` |
| 让 P 证据变充分 | 样本池扩到 ≥120 例（实测每组 60 例时校准集 30 例才达标） |

**回滚**：`algo` 参数回 `v8` 即可，无需改代码；彻底移除则删 `v8/algorithm/` 目录 + 还原 `engine.py` 的三处引用。

## 6. 仍未关闭的（不在本次伪装成已解决）

1. **真实企业数据未接入**：Q/D/P 的判别力无任何外部验证，全部证据都来自合成数据。
2. **合成数据循环验证未破**：数据生成器按 Benford 生成首位数字、按 `_tamper` 注入粉饰，与算法的检验假设同源。本次只是不再把合成结果写成真实性能。
3. **Q 的 Benford 适用性仍未证明**：我的建议是**把 Q 从融合输入降级为数据质量报告**（评审 §6 P0），但这需要业务裁决，本次未做。
4. **缺失值仍是全有或全无**：缺任一指标即整链不可用。真实财报必有缺项，应做分级降级（未做，需要口径确认）。
5. **无样本外泛化指标**：D 层没有 LOO/分层 K 折与 AUC/KS；权重不可识别（已在返回体标注 `权重可识别性: 未保证`）。
6. **无生产监控**：没有 PSI/漂移、分数分布、推翻率、贷后表现回流。
7. **跨平台未实测**：本轮只在 Windows / Python 3.12 验证。Bland 规则与固定种子理论上保证确定性，但 Linux 实跑证据缺失。
8. **无模型制品版本化**：模型只在进程内缓存，重启即重建；没有持久化、没有灰度、没有 A/B。
