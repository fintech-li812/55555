## 裁决一：三层风控模型的计算分工（折中方案）

| 层 | 输出 | 计算位置 | MCP 角色 |
|---|---|---|---|
| 第一层 数据质量门禁 | Q（Benford χ² + Myer 双因子） | **千问表格公式** | 不留计算工具，结果经 `log_to_mysql(event_type=quality_check)` 留痕 |
| 第二层 财务健康判别 | D（改进 DEA-DA，SUMPRODUCT） | **千问表格公式 + 系数表** | 只**存取**系数，不求解 |
| 第三层 异常样本复核 | P（Benford-随机森林舞弊概率） | **MCP 侧 Python 推理** | `rf_predict(features)`，模型离线训练、服务端只推理 |
| 融合判定 | 绿/黄/红 | **千问表格 FUSE(Q,D,P)** | 不参与判定 |

要点：最终灯级永远由表格内的 `FUSE` 决定，MCP 只交出一个"修正因子" P。这是答辩时回应"核心逻辑是否外置"的关键话术——三层里两层在平台内，融合在平台内，唯一外置的是随机森林推理，且其结果不直接产生预警等级。

**推论（需用户确认的唯一调和点）**：`quality_check()` 与 `deada_score()` 两个计算型工具在折中口径下不再存在，其职责被"表格公式 + 事件留痕"取代。因此工具总数不是 v8 的 16，而是 **14**。

### 2.2 event_type 合并枚举（24 值）

v8 的 20 值 ∪ 协议 JSON 的 4 值 = 24，保留协议的条件必填语义：

- v8：`daily_check` `quality_check` `deada_score` `rf_predict` `risk_assessment` `approval` `exception` `config_change` `assumption_analysis` `industry_compare` `param_adjust` `feedback` `onboarding` `root_cause` `dynamic_threshold` `stress_test` `exception_review` `audit_triggered` `payment_verified` `da_coefficients_updated`
- 协议：`risk_warning` `tracking_changed` `parameter_changed` `task_result`
- 条件必填：`event_type ∈ {risk_warning, risk_assessment}` 时强制 `rule_id` + `rule_version` + `risk_level`

### 2.3 数据表清单定稿（10 张 + 1 幂等账本 = 11）

协议 6 业务表（audit_log / feedback_log / param_template / exception_log / stress_test_log / payment_verify_log）+ v8 三层日志 3 张（quality_log / deada_score_log / rf_predict_log）+ 新增系数表 `da_coefficient`（承载 v8 的 `deada_coefficients`）+ 协议 `mcp_request_ledger`。

全部 11 张表统一按协议规范补齐：`tenant_id` `request_id` `source_ref` `occurred_at` `created_at` `actor_id` `supersedes_id`，金额 DECIMAL(20,2)（单位元），时间 DATETIME(6)（UTC），结构化内容 JSON，utf8mb4 + InnoDB，按 §八 建索引与唯一键。

> v8 §8.5 的 9 张表 DDL 与 §8.4 的 REST 代码**作废**，不作为实现蓝本。

### 2.4 运行时依赖

`fastapi` + MCP SDK（Streamable HTTP）+ `PyMySQL` + `scikit-learn`（仅推理）+ `joblib` 或 `onnxruntime`（模型加载）。**不需要 scipy**——DEA-DA 线性规划求解移到参赛队离线脚本，MCP 运行时只读写系数表。
