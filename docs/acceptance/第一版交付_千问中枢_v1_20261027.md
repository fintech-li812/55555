## 1. 第一版落地形态（一个关键简化）

原设计里「前端 → 千问 → 服务器」是串联。第一版改为**两入口并列**：

```text
浏览器 ──→ https://<我们的域名>/          千问办公 ──MCP──→ 同一颗计算心脏
           ├─ 静态：工作台_程序计算版.html            （stdio 已通 / HTTP 待测）
           └─ /api/* → 对外服务 → 计算引擎
                                └→ 钉钉 / 企业微信（出口推送）
```

**为什么这样更稳**：现有前端调的是相对路径 `/api/*`，页面与 API 由同一个服务提供，天然同源——不存在跨域和 HTTPS 混合内容问题。而且它**不要求千问开放任何对外 API**，把原设计里最没把握的「命门二」从阻塞项变成了非阻塞项。

千问那条线（Skill + MCP）保持独立接入，共用同一份计算代码。**金额只有一个出处。**

## 4. 三条防伪造设计（这是第一版最值钱的部分）

1. **推送内容不可被前端伪造**：`/api/notify` 的请求体**只允许 `source_id` 一个字段**。服务端拿到后自己调 `calculate()` 现算一遍再格式化。前端传任何金额都会被拒。
2. **缺字段绝不编造**：引擎没返回的字段一律渲染为「未返回」，不从上次结果补、不估、不填零。已实测。
3. **数据库断连不谎报**：`/api/status` 在配置不全时返回 `degraded` + `database: unavailable`，页面照常加载并明示「保存与回查不可用」，绝不显示「已连接」。

## 5. 部署到服务器：阻塞与顺序

### 5.1 必须先补的环境变量（当前全空，所以数据库不可用）

`Config.from_env()` 要求 5 项：`CF_TENANT_ID` / `CF_COMPANY_ID` / `CF_RESULT_FILE` / `CF_RESULT_SHA256` / `CF_DB_NAME`。

**一个部署时容易踩的坑**：`entry.py` 现有那套是**隔离 QA 配置**（端口 13317、`root` 用户、`cfqa_` 前缀库、`CF_QA_MODE=1`、`CF_ALLOW_FIXTURE=1`）。`config.validate()` 强制规定 **root 账号与 fixture 数据只允许出现在 `cfqa_` 隔离库**——生产直接套用会被拒绝。生产必须：

- 用非 root 专用账号（如 `cf_app`）
- 库名**不得**为 `cfqa_` 前缀
- `CF_QA_MODE=0`、`CF_ALLOW_FIXTURE=0`

另有一条硬限制：`CF_DB_HOST` 只允许 `127.0.0.1` 或 `localhost`（`v1_requires_loopback_or_ssh_tunnel`）。**应用与 MySQL 必须同机**，或走 SSH 隧道。这正好与安全要求「MySQL 只绑 127.0.0.1」一致，不构成冲突。

### 9.2 一个重要红线（改动前必须知道）

`agent_guard.py` 规定：`program_calculation`（程序计算）的结果只有在 `allow_fixture=True` 时才允许保存；而 `config.validate()` 又规定该开关**只允许出现在 `cfqa_` 前缀的隔离库**。

**结论：v1 阶段程序计算的合成结果禁止写入生产库，只能进隔离演示库。** 这不是 bug，是有意的安全设计——要写生产库，结果必须由千问表格产出（`origin=qwen_sheet`）。

因此 `setup_storage.py` 提供 `--qa` 模式建 `cfqa_` 隔离库；不带 `--qa` 则拒绝 `cfqa_` 前缀。
