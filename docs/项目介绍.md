# 现金流风险工作台（Cashflow Risk Workbench）

> 一套面向中小制造企业的**现金流风险三层判别系统**：把「现金还能撑几个月」的事实计算，
> 与「这家企业是否财务异常 / 是否疑似粉饰」的模型判别分开，各自标注来源，
> 不让任何一方伪装成另一方。
>
> 版本：v8 工作台 + 生产算法包 v1.0　｜　最后更新：2026-10-29

---

## 一、项目定位

### 它解决什么问题

中小制造企业的风险管理里有两类信息，性质完全不同，但常被混在一张表里讲：

| | 现金流事实 | 财务风险判别 |
|---|---|---|
| 问的问题 | 账上有多少钱、每月流出多少、还能撑几个月 | 这家企业财务是否异常、报表是否疑似粉饰 |
| 得出方式 | **计算**（从八张业务表相加得出） | **推断**（模型对 15 个财务比率打分） |
| 错了的后果 | 算错了就是算错了，可复核查 | 推断有置信度，不能当成结论 |

混在一起的典型后果是：一个用合成数据跑出来的模型分数，被当成"真实企业风险等级"汇报上去。

本项目把这两条线**物理分开**：

- 现金流事实走已冻结的 v1.2 计算内核，真算，结果可追溯；
- 财务比率是独立登记的合成演示输入，页面与接口都显著标注来源，不混入现金流结果；
- 任何环节求解失败都如实标注降级，不伪装成功。

### 它不是什么

- 不是一个可直接对外授信的产品：当前财务比率输入是**固定种子合成数据**，不代表任何真实企业；
- 不是一个通用 BI：不做可视化大屏，输出是"等级 + 依据 + 证据 + 留痕"的判定链；
- 不伪造数据源：真实数据未接入时，接口如实说明，不会悄悄用假数据顶上。

## 二、整体架构与模块职责

### 2.1 部署拓扑

```
                 浏览器（单一源）
                        │  HTTPS
                    ┌───┴────┐
                    │ Nginx  │  对外 443，location / 与 /v8/ 分别反代
                    └───┬────┘
             ┌──────────┴───────────┐
    127.0.0.1:8000          127.0.0.1:8010
   ┌────────────────┐      ┌──────────────────┐
   │ public_server  │─────▶│    v8_server     │
   │ 页面 + 主 API   │ /v8/ │ 三层风控 + 留痕   │
   │ 同源反向代理     │      └────────┬─────────┘
   └────────┬───────┘                │
            │                  MySQL（只绑 127.0.0.1）
     MCP over HTTP :8123        mfg_v8_risk_log_v1
   （供外部 Agent 调用）
```

**关键设计：同源反向代理而非 CORS。**
页面只访问一个源（`/` 与 `/v8/` 两个 location 指向两个本地进程），
因此页面 CSP 保持同源、后端无需开放跨域。
生产由 Nginx 的 `location /v8/` 完成；开发环境由 `public_server` 内置的同源代理完成，
两者任选其一，**不要同时开**——否则 V8 会被转发两跳。

## 三、核心算法原理与实现思路

三层是**串行证据链**：前一层的输出是后一层的输入，来源优先级 **Q > D > P**——
数据不可信时，后两层的结论失去基础。

输入统一为 15 个财务比率：

```
X1 净资产收益率  X2 资产报酬率  X3 营业利润率  X4 流动比率   X5 速动比率
X6 利息保障倍数  X7 利润总额增长率 X8 营业收入增长率 X9 总资产增长率
X10 应收账款周转率 X11 固定资产周转率 X12 总资产周转率
X13 资产负债率  X14 成本费用利润率 X15 总资产现金回收率
```

### 3.1 第一层 Q：数据质量门禁

**原理。** 数字的首位分布若符合 Benford 定律、末位分布若均匀，说明数字是自然产生的；
人为编造的数字很难同时满足这两条。

**实现。**

1. 对每个指标，取样本池内所有取值的**首位数字**（1–9）与**末位数字**（0–9）；
2. 各做一次 **Monte Carlo 精确检验**（1999 次模拟，固定种子）：

   统计量用卡方距离，p 值由模拟分布给出，**不依赖渐近 χ² 近似**——
   样本量小、期望频数低时，渐近近似会严重失真；
3. 15 个指标 × 2 项检验 = **30 项**，用 **Holm 校正**控制族错误率
   （比 Bonferroni 更有检验力，且仍严格控制 FWER）；
4. `Q = 1 − 拒绝数 / 30`，区间 [0, 1]，越大表示数字分布越接近理论分布。

**已知局限（未隐瞒）。** Benford 的适用对象是自然跨量级的**原始金额**，
而这里用在**派生比率**上（0.156、9.80 这类有界比值），原假设先验就未必成立。
实证结果：整池 100% 换成造假样本，Q 仅从 1.0 降到 0.90。
所以 Q 目前更适合做**数据质量报告**而不是"是否造假"的证据——
这也是 `gate_in_fusion` 开关存在的原因（见第六节）。

### 3.2 第二层 D：DEA-DA 财务健康判别

**原理。** DEA-DA（Data Envelopment Analysis – Discriminant Analysis）把"健康组/风险组"
的分类问题化为一个**线性规划**：求一组权重，使健康组样本得分尽量高、风险组尽量低，
同时控制误判。与 logistic 回归不同，它不假设任何分布，也不需要大样本。

**实现。**

- 训练：构造 LP，变量数为 `2n + 15`（n 为每组样本量），约束为分属两类样本的得分差；
- 求解用 **Bland 规则的两阶段单纯形**（最小下标进基/出基规则），
  **逐位继承基线的 pivot 顺序**——换求解器会让 D 的历史锚点漂移；
- **对偶最优性证书**：独立构造对偶可行解，验证原问题目标值与对偶目标值之差
  （实测间隙 4e-14）。基线路在**冗余约束**上会误判为无解
  （人工变量留在基里就整题判死），此时备选路径接管，
  且**必须持对偶证书才采纳**，返回体标注 `solver` 来源；
- 打分：受评对象的 15 个比率用训练好的权重加权求和，输出 `D`（z-score 加权和与临界值之差）。

**已知局限。** 权重向量**不可识别**：8 个权重的 bootstrap 区间全部包含 0（归一化约束下多重最优），
因此 D 的权重**不能当作"指标重要性"**解读。返回体已标注这一点。

### 3.3 第三层 P：舞弊概率

**实现。**

- 特征 30 维 = 15 个原始比率 + 15 个首位数字**自信息** `−log(p(d))`
  （用固定的 Benford 理论分布，不随样本池变化）；
- 随机森林，**随机子空间**：每棵树只随机取一部分特征，增加树间差异；
- 校准：用**独立留出集**拟合正则 sigmoid（约束 a≥0 保单调），
  把森林的投票比例转成概率。未校准的原始投票比例**不是概率**，
  直接拿它跟 0.7 比是不成立的；
- 质量指标：OOB Brier 分数与 ECE（期望校准误差）。

**已知局限。** 校准集规模有限（默认配置下仅 10 例），sigmoid 参数不可外推；
单种子可复现 ≠ 稳健（8 个种子的 P 跨度实测 0.146，而距阈值 0.7 的余量只有 0.068）。

### 3.4 融合层 FUSE(Q, D, P)：48 格决策表

**这是全系统唯一的裁决点**，规则版本 `fuse-v2.0`。

设计要点：

- 每个输入先**离散化为有序状态**：
  Q ∈ {缺失, 严重不足, 存疑, 达标}、D ∈ {缺失, 风险, 正常}、P ∈ {缺失, 高, 中, 低}；
- 4 × 3 × 4 = **48 种组合**，10 条规则**恰好覆盖 48 种，无重叠、无空洞、无兜底分支**；
- **互斥性**保证判定与规则书写顺序无关（旧实现的 `if/elif` 链依赖书写顺序，是缺陷）；
- 空值 / NaN / 越界 / 上游降级**显式纳入判定**，不把"无法判断"静默当成"无风险"；
- 未命中直接抛 `RuntimeError`——决策表有洞是**实现缺陷**，必须补全规则而不是加兜底。

阈值符号统一为 **≥ 下界**（P=0.7 归入"高"），红灯要求"财务风险 D<0"与"舞弊证据 P≥0.7"同时成立。

### 3.5 证据层：只升不降

融合给出灯色后，再按**证据等级**调整一次，规则是**只升不降**：

- 证据不足 → 绿灯升为黄灯，并标记需人工复核；
- 证据缺失 → 保留原等级，标记需人工复核；
- **从不降档**。

这条规则针对一个真实缺陷：某候选实现把"第三层校准不足"当成"P 不可用"，
结果最危险的样本（D=−0.471、P=0.967）从红灯降到黄灯。
证据不足的正确处置是**进人工复核队列**，不是降低严重度。

## 四、关键数据结构与流程

### 4.1 一次评估的流程

```
engine.assess(industry, scenario, amount, ...)
  │
  ├─ ① 解析开关        config.resolve()   四级：请求 > 环境变量 > 配置文件 > 内置默认
  │
  ├─ ② 建样本池        indicators.build_sample_pool(n)
  │
  ├─ ③ 取池级模型      get_pool_model(pool)   ← 命中缓存则直接复用
  │     ├─ 第一层   quality.quality_gate()     30 项 MC 检验 + Holm
  │     ├─ 第二层   deada.fit()                LP + 对偶证书
  │     ├─ 第三层   forest.train()             60 棵树
  │     └─ 校准     calibration.fit()          正则 sigmoid
  │
  ├─ ④ 单次打分        Q 直接取池级结果；D 一次矩阵乘；P 遍历 60 棵树
  │
  ├─ ⑤ 融合            fusion.fuse(Q, D, P, q_in_fusion=...)   → 48 格表
  │
  ├─ ⑥ 取严            与"现金流缓冲判定（M×K）"取较严格者
  │
  ├─ ⑦ 证据调整        policy.apply_evidence()   只升不降
  │
  └─ ⑧ 组装            现金流事实 + 压力测试 + 分级审批 + 三态跟踪 + 例外回溯
```

### 4.2 池级模型（性能设计的核心）

```python
class PoolModel:
    fingerprint      # 训练参数的指纹，缓存键的一部分
    quality          # 第一层结果（只依赖样本池）
    dead, dead_diag  # 第二层模型 + 求解诊断
    forest_model     # 60 棵树
    calibration      # sigmoid 参数
    build_seconds, pool_size
```

**为什么必须把训练与打分分离：** 原先每个请求都要
重建样本池 → 重算 30 项 MC 检验 → 重解 LP → 重训 60 棵树 → 重跑校准，
而这四步**全都只依赖样本池**，与受评对象无关。
实测单个请求 0.26 秒里 99% 是这些池级计算。

分离后请求只剩 60 次树遍历 + 一次矩阵乘。

### 4.3 返回体要点

```jsonc

  "算法版本": "ra-next-v1.0",
  "生效开关": { "算法版本": "v1", "证据模式": "strict", "Q参与融合判别": true, ... ,
               "取值来源": { "算法版本": "请求参数", ... } },
  "现金流事实": { "期末现金": ..., "月均经营性流出M": ..., "ok": true },
  "第一层": { "Q": 0.9333, "明细": {...}, "适用性声明": "..." },
  "第二层": { "D": 0.187676, "最优性确认": true, "求解器": "...", "权重": {...} },
  "第三层": { "P": 0.8312, "P_raw": ..., "OOB_Brier": ..., "树数": 60 },

## 五、技术选型理由

| 选择 | 理由 |
|---|---|
| **纯标准库实现 LP 与森林** | 生产环境无法保证 numpy/scipy 可用；自实现才能保证数值逐位可复现。代价是要自己处理退化与冗余，收益是零依赖、可迁移、可审计 |
| **继承基线 Bland 单纯形的 pivot 路径** | 换求解器（哪怕更先进）会让 D 的历史锚点漂移，留痕就对不上。数值兼容优先于数值先进 |
| **独立对偶证书** | 单纯形的浮点结果不是证明。用对偶可行解验证间隙（实测 4e-14），才能声称"最优" |
| **MC 精确检验而非 χ² 近似** | 样本量小时渐近近似失真严重；模拟次数固定 1999 次 + 固定种子，保证可复现 |
| **随机子空间 + 独立留出集校准** | 子空间增加树间差异；留出集与训练分离，避免用训练数据校准导致的过度自信 |
| **同源反向代理而非 CORS** | CSP 保持同源，后端不必开放跨域；主站代理层还能校验目标地址只允许回环，避免被当内网代理滥用 |
| **48 格互斥决策表** | 消除"区间边界怎么算""两个阈值之间算什么"这类歧义；判定与书写顺序无关；漏格会在测试里直接暴露 |
| **训练/打分分离 + LRU 缓存** | 池级产物与受评对象无关，复用后单次评估提速 15× |
| **per-key 构建锁（非全局锁）** | 8 线程并发做纯 Python CPU 密集计算会互相抢 GIL，实测 P95 从 1.3s 恶化到 9.7s。per-key 锁让同池请求共享一次构建，不同池仍可并行 |
| **MySQL 只绑 127.0.0.1** | 与应用同机，不暴露到公网；账号按 DML/DDL/备份分离 |

## 六、配置与开关

带业务口径含义的行为全部**可配置**，四级取值：

```
请求参数  >  环境变量 CF_V8_*  >  deploy/algorithm.config.json  >  内置默认
```

| 开关 | 默认 | 关闭→打开的效果 |
|---|---|---|
| 算法版本 | `v8` | v8 / ra-next-0.1 / v1 三选一 |
| 证据模式 | `strict` | 证据不足不发放绿灯 → 恢复三档判别 |
| Benford 适用性 | 未声明 | 三态：未声明 / 已论证 / 不适用 |
| **Q 参与融合判别** | 参与 | Q 只作数据质量报告，不参与判别与证据短板 |
| 稳定性 bootstrap | 关 | 附 30 次分层 bootstrap（+1~2s） |
| 池级模型缓存 | 开 | 关掉回到每请求全量重算（行为不变，只变耗时） |
| 每组样本量 | 20 | 区间 [2, 60] |
| 森林树数 | 60 | 区间 [1, 500] |

**默认全部等于加开关之前的原有行为**——不配置任何东西时表现逐位一致。
完整说明见 `docs/operations/算法开关说明.md`。

`Q 参与融合判别 = false` 的实现方式值得单独说明：
它在**输入规范化阶段把 Q 状态钉成「达标」**，等价于取 48 格表在 `Q=Q_OK` 上的子表，
**不新增规则、不改任何一格**，物理上无法分叉；
但 Q 本身的证据等级**照实记录**（不假装充分），只是排除在短板计算之外——
否则"让 Q 退出判别"与"Q 证据不足卡住绿灯"会互相抵消，开关开了等于没开。

## 七、时间与空间复杂度 / 性能考量

### 7.1 实测数据

| 项目 | 数值 |
|---|---|
| 单次评估（v8 基线） | 0.2675 s |
| 单次评估（ra-next-0.1） | 0.1234 s |
| **单次评估（生产版 v1，缓存命中）** | **0.0179 s**（15× 提速） |
| 池级模型内存 | ≈ 76 KB（60 棵树 + 权重 + 校准参数） |
| 并发 8 线程 × 6 次（修复前） | 26.94 s，P95 9.72 s |
| **并发 8 线程 × 6 次（修复后）** | **0.94 s，P95 0.24 s** |

### 7.2 复杂度

| 环节 | 复杂度 | 说明 |
|---|---|---|
| 第一层 Q | O(n) + O(S·m) | n 样本、m=30 项、S=1999 次模拟，与受评对象无关 |
| 第二层 D 训练 | **约 O(n³)** | 瓶颈：LP 的变量数为 2n+15 |
| 第二层 D 打分 | O(k) | k=15，一次加权求和 |
| 第三层 P 训练 | O(T·s·d·log d) | T=60 棵树、s 子样本、d 特征维数 |
| 第三层 P 打分 | O(T·depth) | 60 次树遍历 |
| 融合 | O(1) | 48 格表查表 |

**关键结论：所有高开销环节都只依赖样本池，与受评对象无关**，
所以缓存才能带来 15× 提升。

### 7.3 样本量上界为什么是 60

池级模型构建随规模**三次增长**（瓶颈是 DA 的 LP）：

| 每组样本量 | 池大小 | 构建耗时 |
|---:|---:|---:|
| 20 | 40 | 0.30 s |
| 40 | 80 | 1.63 s |
| 60 | 120 | 6.95 s |
| 100 | 200 | 39.8 s |

60 是硬上界：再往上既是 DoS 入口（接口被一个 `n=999999` 拖死），收益也很有限。
60 刚好满足「P 层证据充分」所需的规模（每组 60 时校准集才够 30）。

```
/opt/cashflow/

三个 systemd 服务：

| 服务 | 端口 | 说明 |
|---|---|---|
| `cf-workbench` | 8000 | 对外页面与主 API（含同源反代） |
| `cf-v8-web` | 8010 | V8 三层风控服务 |
| `cf-mcp-http` | 8123 | MCP over HTTP（供外部 Agent） |

Nginx：`location /` → 8000，`location /v8/` → 8010。

### 9.2 一键部署

```bash
# 只放行 HTTP 出站的网络里，SSH 走 CONNECT 隧道
export CF_SSH_PROXY="http://<proxy>:<port>"

python scripts/deploy_server.py --host <IP> --dry-run   # 先看清单
python scripts/deploy_server.py --host <IP>             # 真正部署
```

流程：**备份 → 上传（逐字节核验）→ 远端语法检查 → 重启 → 健康轮询 → 开关行为核验**。
任一步失败立即停止，不留下半截部署；回滚目录在输出末尾给出。

### 9.3 敏感信息

- `deploy/.env` 含数据库口令、鉴权令牌等，**被 gitignore，绝不入库**；
  需要配置项时提交 `deploy/env.template`（只含键名，值为空）；
- 公开仓库不保留真实 IP/域名，文档里统一用占位符；
- 推送脚本在推送前后各扫描一次：敏感文件、真实地址、明文口令，发现即中止。

## 十、已知限制与后续可扩展方向

### 10.1 明确未解决（不伪装成已解决）

| 限制 | 影响 |
|---|---|
| **真实数据未接入** | 财务比率是固定种子合成数据，模型输出不代表任何真实企业 |
| **合成数据的循环验证** | 生成器按"健康组符合 Benford、风险组施加粉饰"构造，等于**生成假设 = 检验假设**，模型在合成数据上的表现不能外推 |
| **Q 的 Benford 适用性未证明** | Q 检出力极低（整池造假仅从 1.0 降到 0.90），建议把 Q 从融合输入降级为数据质量报告 |
| D 层无样本外验证 | 没有 LOO / AUC / KS；权重不可识别（已在返回体标注） |
| 缺失值全有或全无 | 缺一个指标即整链不可用，没有逐指标降级 |
| 无 PSI 漂移监控 | 模型上线后没有分布漂移告警 |

### 10.2 建议的演进方向（按优先级）

1. **接真实数据 + 破循环验证**：用真实标注样本重训并做 LOO/AUC/KS，
   同时保留合成数据作为回归基线；
2. **重标 Q 阈值或改刻度**：当前 Q 实测区间 [0.93, 1.0] 而融合阈值是 0.3/0.5
   （旧 χ² 尺度遗留），第一层几乎不起作用。要么重标阈值，要么把 Q 移出判别链
   （开关已就绪，只待业务裁决）；
3. **逐指标降级**：缺失一个指标时只禁用依赖它的检验，而不是整链判死；
4. **多种子平均**：第三层改为多种子平均 + 报告方差，替代单种子点估计；
5. **PSI 漂移监控**：对 15 个比率与三层得分做分布漂移告警；
6. **动态阈值接入**：`policy.threshold_policy`（静态下限 + 月份连续性）已实现为候选，
   尚未接线——它有"静态下限防止越差越宽松"的设计，是真正的业务洞察；
7. **审批留痕与工单闭环**：当前留痕是日志表，未与复核工单联动。
